## 2026-09-14 — #146: auth-client lock race — singleton disproven as a fix, backstop fixed and verified, NOT Done

### Changed

- **`utils/supabase/client.ts`** (`docs/briefs/146-fix-auth-client-lock-race.md`): converted `createClient()` to a module-level singleton, per the brief's stated root-cause fix. Checked all 19 call sites first — none pass per-call options or depend on getting a fresh instance (the two `auth.signOut()` sites already do manual cookie/localStorage cleanup rather than relying on client freshness), so the change itself is safe. **Live verification then disproved it as the actual fix** (see Decisions/Live-verification below) — kept in the codebase anyway as reasonable practice (one `GoTrueClient` per tab instead of N), with its comment corrected to say plainly that it does not fix #146's race.
- **`app/path/page.tsx`**: entry-gating `useEffect` (`init()`) wrapped in try/catch; new `'error'` `PageState` renders `MessageState` with a "Try again" retry button that resets state and re-runs the effect via a new `entryRetryKey` dependency. Extended beyond the brief's original spec after live testing found a real gap: `supabase.auth.getUser()` doesn't always throw — a retryable fetch failure resolves as `{ data: { user: null }, error: AuthRetryableFetchError }`, which the original `const { data: { user } } = await supabase.auth.getUser()` destructuring silently discarded, landing on `'anonymous'` instead of the new error state. Added an explicit `error` check (`isAuthSessionMissingError` from `@supabase/supabase-js` excluded, since that one genuinely means "not logged in" and should still map to `'anonymous'`) that throws into the same catch block.
- Nothing else touched — `Header.tsx`/`BottomNav.tsx`/`utils/supabase/server.ts`/`utils/supabase/middleware.ts`/Path Report/Options/Direction all untouched, per the brief's stop conditions.

### Decisions

- **Singleton kept but not trusted as the fix.** Traced into `@supabase/auth-js`'s `GoTrueClient.getUser()` (`_acquireLock` at `GoTrueClient.ts:1900`): the navigator lock name is derived from `storageKey`, not client-object identity, and every `getUser()` call independently calls `navigator.locks.request` with that same name — no in-flight de-duplication on the client object. So Header/BottomNav/`/path`'s own effect still fire 3 concurrent lock requests whether or not they share one `createClient()` instance. Confirmed via a forced-race repro (below): 25/25 failures both with the pre-fix multi-instance code and the post-fix singleton, identical error shape both times, re-run against a freshly rebuilt dev server to rule out a stale-bundle artifact. The actual fix needs to dedupe/serialize the concurrent `getUser()` calls across components — out of this ticket's scope (would touch `Header.tsx`/`BottomNav.tsx`). Not filed as its own ticket yet.
- **Backstop scope extended past the brief's literal spec**, on explicit instruction this session, once the `AuthError`-swallowing gap was found live — the brief's own motivating case (#141-shaped transient Supabase outage) is exactly the shape that would have been silently misread as `'anonymous'` without this extra check, so leaving it out would have meant the backstop didn't actually cover its own stated motivation.
- Explicit instruction this session: do not extend scope to `Header.tsx`/`BottomNav.tsx` to fix the real lock race, even though the investigation surfaced enough to know roughly what that fix would look like. Ticket stays open rather than silently working around the disproven root-cause fix or reframing the result.
