## 2026-09-14 — #146: auth-client lock race — singleton disproven as a fix, backstop fixed and verified, NOT Done

### Changed

- **`utils/supabase/client.ts`** (`docs/briefs/146-fix-auth-client-lock-race.md`): converted `createClient()` to a module-level singleton, per the brief's stated root-cause fix. Checked all 19 call sites first — none pass per-call options or depend on getting a fresh instance (the two `auth.signOut()` sites already do manual cookie/localStorage cleanup rather than relying on client freshness), so the change itself is safe. **Live verification then disproved it as the actual fix** (see Decisions/Live-verification below) — kept in the codebase anyway as reasonable practice (one `GoTrueClient` per tab instead of N), with its comment corrected to say plainly that it does not fix #146's race.
- **`app/path/page.tsx`**: entry-gating `useEffect` (`init()`) wrapped in try/catch; new `'error'` `PageState` renders `MessageState` with a "Try again" retry button that resets state and re-runs the effect via a new `entryRetryKey` dependency. Extended beyond the brief's original spec after live testing found a real gap: `supabase.auth.getUser()` doesn't always throw — a retryable fetch failure resolves as `{ data: { user: null }, error: AuthRetryableFetchError }`, which the original `const { data: { user } } = await supabase.auth.getUser()` destructuring silently discarded, landing on `'anonymous'` instead of the new error state. Added an explicit `error` check (`isAuthSessionMissingError` from `@supabase/supabase-js` excluded, since that one genuinely means "not logged in" and should still map to `'anonymous'`) that throws into the same catch block.
- Nothing else touched — `Header.tsx`/`BottomNav.tsx`/`utils/supabase/server.ts`/`utils/supabase/middleware.ts`/Path Report/Options/Direction all untouched, per the brief's stop conditions.

### Decisions

- **Singleton kept but not trusted as the fix.** Traced into `@supabase/auth-js`'s `GoTrueClient.getUser()` (`_acquireLock` at `GoTrueClient.ts:1900`): the navigator lock name is derived from `storageKey`, not client-object identity, and every `getUser()` call independently calls `navigator.locks.request` with that same name — no in-flight de-duplication on the client object. So Header/BottomNav/`/path`'s own effect still fire 3 concurrent lock requests whether or not they share one `createClient()` instance. Confirmed via a forced-race repro (below): 25/25 failures both with the pre-fix multi-instance code and the post-fix singleton, identical error shape both times, re-run against a freshly rebuilt dev server to rule out a stale-bundle artifact. The actual fix needs to dedupe/serialize the concurrent `getUser()` calls across components — out of this ticket's scope (would touch `Header.tsx`/`BottomNav.tsx`). Not filed as its own ticket yet.
- **Backstop scope extended past the brief's literal spec**, on explicit instruction this session, once the `AuthError`-swallowing gap was found live — the brief's own motivating case (#141-shaped transient Supabase outage) is exactly the shape that would have been silently misread as `'anonymous'` without this extra check, so leaving it out would have meant the backstop didn't actually cover its own stated motivation.
- Explicit instruction this session: do not extend scope to `Header.tsx`/`BottomNav.tsx` to fix the real lock race, even though the investigation surfaced enough to know roughly what that fix would look like. Ticket stays open rather than silently working around the disproven root-cause fix or reframing the result.

## 2026-09-14 — #146 addendum: real fix — dedupe concurrent getUser() calls — code + synthetic verification complete, NOT Done (real checkout pass outstanding)

Same day, same ticket, the follow-up flagged in the entry above as needing its own ticket turned out to get done directly under #146 instead, per `docs/briefs/146-addendum-dedupe-getuser.md` ("staying under #146, not a new ticket"). This is the entry with the real fix and its verification — but it does not close #146 (see Next): the original brief's Stripe test-mode checkout pass has still never actually been run.

### Changed

- **New `lib/use-auth-user.tsx`**: `AuthUserProvider` (mounted once at `app/layout.tsx`, wrapping `Header`/`{children}`/`BottomNav`) + `useAuthUser()`. Calls `createClient().auth.getUser()` exactly once per full page load and shares `{ user, loading, error }` with every consumer via React Context — the actual fix. No `onAuthStateChange`, no polling: matches every existing call site's own "one fetch per page load" behavior, deliberately not new reactivity, per the addendum's own stop condition.
- **Converted every independent `createClient()` + `getUser()`/`getSession()`-on-mount call site to the shared hook**: `components/Header.tsx` (simplified further — no longer needs its own `useEffect`/state at all, initials derived directly from the hook's `user` at render time), `components/BottomNav.tsx`, `app/path/page.tsx`, `app/dashboard/page.tsx`, `app/account/page.tsx`, `app/identity/page.tsx`, `app/plan/page.tsx`, `app/start/page.tsx` (ordering-sensitive: `clearStorageUnlessOwnedBy` still runs synchronously first inside `resolveMode`, now gated on the hook's `loading` flag resolving rather than its own `getUser()` call). `app/login/page.tsx`/`app/signup/page.tsx` audited per the addendum's list and confirmed to never call `getUser()`/`getSession()` at all — genuinely nothing to change there, not skipped by oversight.
- **`components/IdentityCard.tsx` + `components/MomentumCard.tsx`** — found mid-verification, not on the addendum's own page-level audit list (it named pages, these are components): both render together on `/dashboard` and each independently called `createClient()` + `getUser()` on mount, the identical bug at component granularity. First forced-race repro against `/dashboard` caught it directly (2 `/auth/v1/user` requests instead of 1, see Live-verification) — converted both to the shared hook the same way, re-verified 1/1.
- **`app/mentor/page.tsx`**: initial `getSession()` call replaced with a hook-seeded effect (`if (authHookLoading) return; setIsAuthenticated(!!authUser); setAuthChecked(true);`) — its own separate concurrent lock acquisition. Its `onAuthStateChange` subscription is explicitly KEPT, not removed — flagged before touching (see Decisions) since the addendum brief's own stated assumption ("none of the current call sites subscribe to `onAuthStateChange`") turned out to be wrong for this one file.
- **Two deliberate exceptions, not touched**: `app/path/page.tsx`'s retry button and `app/identity/page.tsx`'s `handleRetry` both still make their own direct, fresh `getUser()` call rather than reusing the shared hook's one-shot cached value — both fire well after mount, in response to a user click, never concurrent with the shared hook's own fetch, so a direct call there doesn't reintroduce the race; reusing the cached value instead would make "Try again" retry nothing, since the hook never refetches.

### Decisions

- **Stopped and asked before touching `app/mentor/page.tsx`**, per the addendum's own stop condition on unplanned reactivity changes. The addendum assumed no page used `onAuthStateChange`; mentor actually does, and traced that both its `getSession()` call and the subscription's own initial-session emit independently acquire the same navigator lock (confirmed in `@supabase/auth-js`'s `onAuthStateChange` → `_emitInitialSession` → `_acquireLock`), so mentor contributes 2 concurrent acquisitions per mount, not 1. Explicit correction from the user: mentor's chat is fully built and only unreachable by real users today because subscription billing (#30) hasn't shipped — its live reactivity (session expiring or completing in another tab mid-conversation) is real, load-bearing behavior for when #30 ships, not dead-code incidental reactivity. Landed as: dedupe the initial check via the shared hook, keep the subscription. One non-deduped lock acquisition remains on `/mentor` specifically — a deliberate, logged trade-off, not an oversight, and not part of the "0 lock-contention" requirement verified below (that was checked against `/path` and `/dashboard`, not `/mentor`).
- Did not re-run the original brief's Stripe test-mode checkout pass — `NEXT_PUBLIC_SITE_URL` isn't set in `.env.local`, so `/api/checkout`'s `success_url`/`cancel_url` don't resolve to a usable local redirect. Out of this addendum's own stated verification requirements (forced-race repro + Header/BottomNav browser pass only) — not chased further, not silently worked around by editing `.env.local`.
- `IdentityCard`/`MomentumCard` converted without asking first, unlike mentor — these were a straightforward instance of the exact same bug the addendum describes (independent mount-time `getUser()` call), with no behavior trade-off attached, so no stop-and-report was warranted; mentor's case was different specifically because it meant removing something (existing reactivity), not just deduping a call.
