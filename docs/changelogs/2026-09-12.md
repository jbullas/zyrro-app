## 2026-09-12 — #138 Options rewrite: semantic alignment check, card redesign, refine-flow UI fixes — committed, live-verified

### Changed

- **§5 — semantic alignment check** (new, this session): `lib/prompts/path-options-semantic-check.ts` — an independent LLM judge, separate from the generation prompt so it has no visibility into how or why a draft was produced. Real captured failure that motivated it: 2/4 options for an Amara-like profile were team-leadership-framed in substance ("Strategic Team Builder," "Outcome-Focused Mentor") against explicit delegation/team-management must-avoids, with zero hits from the existing phrase-match hard check. No negative-word-list expansion (explicitly rejected as the same brittle mechanism at larger scale) — judges substance holistically instead. Wired into `generate-path-options-session.ts` as hard check 4: one batched call per generation attempt (not per option), semantic-fail treated exactly like a must-avoid hit in the accept/reject/retry control flow, and — per this session's confirmed decision — the judge's own real reasoning always goes into the retry steer verbatim, never a generic template, for semantic-only rejections.

- **`fit_score`/`fit_confidence` parsing** (`generate-path-options-session.ts`): validated *leniently and independently* of `pass`/`reasoning` — a malformed or missing value in either new field nulls out only that field, never the surrounding verdict, and never triggers the existing fail-closed fallback. This is what keeps the §6 extension genuinely additive: gating behavior is provably unchanged from before the extension, confirmed by re-running the real entrepreneur/must-avoid scenario and comparing rejection shapes before/after.

### Decisions

- Semantic check stays scoped to alignment only, not also distinctness between options — the existing material-duplicate check's own theoretical brittleness (phrase-overlap could miss a semantic duplicate) hasn't been observed as a real captured failure, so it's out of scope per this project's "fix real captured failures, not speculative ones" discipline. The batched-per-round architecture would allow that extension later without a redesign, if ever needed.
- `tension`/`core_statement` are deliberately **not** scanned by the existing must-avoid/duplicate hard checks. Reason: `tension` is designed to sometimes name must-avoid-adjacent territory as an honest, non-negated partial-overlap caveat — scanning it with the same phrase-match check would false-positive on exactly the content the field exists to contain.
- `fit_score`/`fit_confidence` payload to the judge stays `must_haves`/`must_avoids`/`ideal_life` + drafts only — deliberately not `signatures`/`how_you_operate`. The judge checks alignment with what the person stated, not whether an option correctly extrapolates their identity pattern (the generation prompt's job, not this independent check's).
- Comments acknowledgment is a single static line for the whole `report.loading` duration, no timer/fade/transient mechanism. Reason: report generation is comparable in length to Options generation (a real wait, not instant), and a timed show-then-hide would be new UI mechanism the session explicitly ruled out; `GeneratingState`'s `description` prop already works this way everywhere else in the codebase.
- The deeper "make the comment feel read" design (e.g., surfacing it inside the report itself) is deferred to `#139`, once that report's actual prompt is rebuilt under the life-path framing and can be verified for real — not guessed at here.
