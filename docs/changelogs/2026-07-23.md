### Decisions
- **Keep deleting `failed` identity_report rows in `kickoffIdentityGeneration`**
  (the brief's open question — explicitly logging the call either way, not
  blocking on it). A `failed` row has no meaningful content (the LLM call
  never completed) — it's noise, not history worth the append-only
  guarantee. Retention is now the *default* for real generations
  (ready/failed-with-content-attempted rows from actual runs stay forever),
  but an empty-content failed stub isn't in that category. Low-risk either
  way; picked the option that keeps the artifacts table free of rows with
  no informational value.
- **`path_options`/`path_plan`'s write paths are not actually append-only**,
  contradicting the brief's stated premise ("path_options and path_plan
  already work this way"). `generate-path-options/route.ts`,
  `generate-path-plan.ts`, and `select-path/route.ts` all UPDATE an
  existing row in place when one's found for the relevant key
  (user+type, or the selection's `path_options_artifact_id`+`path_id`) and
  only INSERT when none exists — singleton-by-construction, not
  history-preserving. This is *why* the selection-scoped read sites listed
  above don't need `getCurrentArtifact`: there's never more than one row to
  disambiguate today. Did not touch this — changing insert-vs-update
  branching is a real scope expansion beyond what this ticket asked for,
  and out of scope per the brief's boundaries (no #60 regen UI, no /start
  changes). Flagging for a future ticket if `path_options`/`path_plan`
  should actually become append-only to match the documented policy.
- **`seedArtifact`'s identity_report delete: revised mid-session after a
  race was flagged.** First pass narrowed the delete to `status =
  'generating'` only, matching the new index. That's unsafe: bootstrapping
  a test user fires `kickoffIdentityGeneration()` in the background via
  `/auth/callback`, and its row's status by the time `seedArtifact` runs
  isn't guaranteed to still be `'generating'` — under a fast/mocked LLM
  backend or slow test-harness startup it could already be `ready` or
  `failed`, leaving a stale duplicate the narrowed delete wouldn't catch.
  Confirmed this isn't fully absorbed by "all reads go through
  `getCurrentArtifact`" either: `kickoffIdentityGeneration`'s own
  idempotency check uses `.maybeSingle()` with no ordering, which throws on
  more than one matching row — a real failure mode for any verification
  flow that re-triggers kickoff-style logic against a seeded user. Reverted
  to deleting by type only (any status). `seedArtifact`'s contract is "one
  deterministic row per call," not exercising history — tests that
  specifically want coexisting rows (like this session's own scenario 2
  verification) insert the second row directly, bypassing this guard.

### Decisions
- **Idempotency check moved into `completeDiscovery`, not left in
  `kickoffIdentityGeneration`.** Caught mid-session, not by me: the first
  draft of `POST /api/complete-discovery` called `completeDiscovery` with no
  protection against resubmission (double-click, back-button-and-resubmit,
  retry-after-a-slow-but-successful-response) — since #59's unique index
  only blocks a second `generating` row, not a resubmission after `ready`,
  nothing would have stopped a second full paid LLM generation for a user
  who already had a report. Fixed by moving the existing-artifact check
  from `kickoffIdentityGeneration` into `completeDiscovery` itself, so both
  callers share one check instead of `kickoffIdentityGeneration` owning a
  copy the new route never got.
- **`QuestionAnswerList` revised from bare `.report-section` blocks to
  `.card`-wrapped items — verify class reuse against actual rendered
  output, not name-matching.** First draft picked `.report-section` by
  pattern-matching the class name against `/identity`'s markup, without
  checking what it actually looks like rendered — challenged twice in
  review before I did. Live screenshots of `/identity` showed
  `.report-section` is a bare spacing wrapper with no visual separation of
  its own; the app's actual established pattern for *repeated* list items
  (TOC rows inside a card, `ConstellationCard` for signature lists) is a
  bordered white `.card`/`.constellation-card` treatment. Revised to wrap
  each Q&A item in `.card`; confirmed via live screenshot (all 13 items,
  full scroll) that this renders correctly with proper text wrapping and
  clear separation between entries.
- **Mode-resolution fallback on a `discovery_answers` query error → State 3,
  not State 1.** Undocumented edge case, not asked for either way in the
  brief. A logged-in user is already authenticated, so falling back to the
  anonymous `signUp()` flow would be actively wrong (attempts to create a
  second account for an existing user). State 3's submit path still works
  off the real session regardless, so it's the safer default.
- **Known gap, not fixed — flagging rather than silently leaving it**:
  `/api/retry-generation` → `kickoffIdentityGeneration(user)` derives
  answers exclusively from `user.user_metadata.discovery_answers`. A
  State-3-originated user's metadata *never* has discovery_answers (they
  never signed up with that metadata) — so if their `completeDiscovery`-driven
  generation fails, the existing "Try again" button on `/identity` will
  silently no-op for them forever (the new empty-answers guard causes an
  immediate `return false`), even though they have real `discovery_answers`
  rows in the DB. Out of this brief's explicit scope (not mentioned, and
  fixing it means teaching the retry path to fall back to DB-sourced
  answers) — needs its own follow-up ticket before #20 users can be assumed
  to have a working retry path.

- **Tooling lesson for future one-off verification scripts** (not shipped

  worth keeping): `verify-20-state1.mts` initially crashed with an
  uncaught `TimeoutError` mid-run, which skipped its `finally` cleanup
  entirely for a real Supabase auth user created via client-side `signUp()`
  — its ID was only known via a post-hoc lookup-by-email *inside* the `try`
  body, so a throw before that lookup ran meant the user was never found,
  never deleted. Fixed by (1) wrapping the run in `try { ... } catch (err) {
  record as failure } finally { cleanup }` so a thrown error is recorded
  and doesn't skip cleanup, and (2) re-deriving the created user's ID by
  the same email lookup *inside* `finally` as a backstop, independent of
  whether the `try` body ever reached its own lookup. General lesson: any
  one-off script that creates a resource whose ID isn't returned
  synchronously (only discoverable via a later lookup) must do that lookup
  in `finally`, not just in the happy path — otherwise any exception
  between creation and lookup orphans the resource.
