## 2026-09-11 — #134 Slice 3: "Your Path" final delivery backend (schema, generation, API, naming) — script-tested, UI not yet built

### Changed

- New `path_report` artifact type (migration `20260910010000_path_report.sql`).
  Tier C append-only (`generating`/`ready`/`failed` — Tier C's own standard
  vocabulary, no widening needed there), not a mutated-in-place session like
  `path_direction_session`/`path_options_session`: this is a genuine
  permanent deliverable with no checkpoint/redo (brief §5 — no user-facing
  accept/adjust on the report content itself). Standard Tier C race guard
  (partial unique index on `generating`), same shape as `identity_report`'s
  own precedent.
- `lib/prompts/path-report.ts` + `lib/generate-path-report.ts` — new,
  standalone generation logic. Deliberately does **not** call or adapt
  `runStage5Develop`/`runStage6Report` (`lib/generate-path-checkpoint.ts`) —
  those expect a richer per-signature `evidence_citation`/`desire_citation`/
  `grounded_in` shape the old Stage 1-4 capability/desire-intersection
  pipeline produced, which Direction/Options don't produce (confirmed via
  reading their real prompts before writing anything, not assumed). Reuses
  `findMustAvoidViolations` from `lib/generate-path-options-session.ts`
  (Slice 2's negation-aware check) as defense-in-depth, scanned across every
  text field including each `master_strategy` objective — reasoned through
  explicitly why the risk is lower than Options faced (no explicit
  "explain avoidance" instruction) but not zero (`must_avoids` still in
  context; `honest_cost` is a plausible reassurance-framing target) before
  deciding to reuse it, rather than silently assuming either way.

  Two real bugs surfaced by the first live LLM run against this prompt
  (`scripts/test-134-slice3-report-checks.mts`), not assumed away:
  - **Literal placeholder brackets**: the prompt's own worked example used
    `"[timeframe]"`-style notation illustratively; the model copied it as
    real syntax into two of three `master_strategy` names. Fixed by
    rewriting the example with fully concrete text (no brackets) plus an
    explicit anti-placeholder instruction, backed by a log-only
    `logPlaceholderBracketsInReport` check (polish issue, not a
    trust/compliance one — no retry).
  - **`life_it_leads_toward` restating `ideal_life`** near-verbatim instead
    of developing it. Same failure class `enforceConstellationSynthesisNonOverlap`
    already solved for `constellation_synthesis` vs `identity_thesis`
    (`lib/generate-identity-report.ts`) — same fix applied
    (`enforceLifeLeadsTowardNonOverlap`, strips an overlapping sentence,
    won't empty a required field), not reinvented. Its helpers aren't
    exported from that file, so a small local duplicate lives in
    `generate-path-report.ts` — same situation `generate-path-options-session.ts`
    was already in for its own overlap check.

  Re-ran the real test after both fixes (a fresh generation, not the same
  cached output) — confirmed the actual fix, not assumed from the first
  run: zero placeholders, `life_it_leads_toward` reads as real elaboration.
- `app/api/path-report/route.ts` (new) — GET only, no POST: unlike
  `path_options_session`, this artifact has no user-facing mutation on its
  own content. Loads `path_options_session` (409 if no
  `selected_candidate_id`), `path_direction_session` (409 if not
  `complete`), `identity_report`. Standard Tier C creation-race pattern
  (insert/catch-`23505`/reread), not `path_options_session`'s
  `claimGeneration`-based session pattern. Resumes a `status: 'failed'` row
  on GET (claim + re-run) — applying Slice 2's own GET-resume lesson from
  the start this time, not repeating that gap.
- `lib/artifacts.ts` — `ArtifactType` widened for `path_report` (same
  recurring gap as `path_options_session` — caught by a real `tsc` error
  again, not inspection).
- `lib/prompts/project-name.ts` rewritten — drops the old `{ name, thesis,
  signatures_engaged }` input shape entirely (checked the live prompt
  before assuming it could be adapted in place: it explicitly required
  `signatures_engaged` and instructed the rationale to reference it, same
  old-shape problem Stage 5/6 had, just smaller). Takes `path_report`'s
  real `chosen_candidate` `{ name, description }` directly.
- `app/api/generate-project-name/route.ts` + `app/api/name-path-result/route.ts`
  adapted in place (same route paths — "project naming" is the feature name
  from #10, independent of which artifact backs it; this is the *second*
  time this exact pair has been migrated in place, following the precedent
  their own prior comment already set). Both now resolve the current user's
  `ready` `path_report` server-side via `getCurrentArtifact` instead of
  trusting a client-supplied id — a deliberate tightening, matching
  `/api/path-options`'s own POST convention.
- Naming routes deliberately kept **separate** from `path-report`'s own
  route rather than folded in as `action: 'set_name'`/`'skip_name'` —
  naming is itself a two-step LLM-backed flow (generate 3 suggestions, then
  persist a pick/skip), not a plain mutation on the report's own generation
  lifecycle; reasoned through both options before choosing, not defaulted
  to Options' single-route-multiple-actions shape just because it was
  adjacent.
- `scripts/test-134-slice3-report-checks.mts` and
  `scripts/test-134-slice3-project-name-checks.mts` — new live-output test
  scripts, see Verification below.

### Decisions

- New, standalone prompts for both `path_report` and project naming — not
  bridging into the old Stage 5/6 or old naming shapes. Why: neither old
  shape's required fields (`evidence_citation`/`desire_citation`/
  `grounded_in`/`signatures_engaged`/`thesis`) exist in Direction/Options'
  actual output; fabricating them to satisfy the old prompts would mean
  inventing citation structure the new flow never computed, breaking the
  same grounding discipline those old checks exist to enforce.
- `path_report` is Tier C, not a mutated-in-place session. Why: it's a
  genuine one-time deliverable with no checkpoint/redo, unlike Direction/
  Options — matches `identity_report`/`path_options`/`path_plan`'s existing
  pattern rather than Slice 1/2's session pattern.
- No dedicated `lib/path-report.ts` data-access module. Why: this artifact's
  CRUD is simple enough (no state machine beyond one failed-row-resume
  case) that inline-in-the-route is proportionate, matching how
  `identity_report`'s own kickoff isn't backed by a dedicated session
  module either — a judgment call, not a settled precedent, flagged as such
  when proposed.
- Naming stays two separate routes, not folded into `path-report`'s route.
  Why: naming is conceptually a distinct sub-feature (its own LLM call,
  bolted on after the report is already `ready`), not part of the report's
  own generation lifecycle — and there's already a real, twice-used
  precedent for adapting these exact two routes in place rather than
  reinventing their shape.
- Both naming routes resolve the current user's `path_report` server-side
  via `getCurrentArtifact`, not a client-supplied id. Why: matches
  `/api/path-options`'s POST convention (can't be pointed at another
  artifact via a tampered id), and simplifies the eventual client (no id to
  track/pass).

## 2026-09-11 (session 2) — #134 Slice 3: "Your Path" UI, naming, and a get-or-create bug found+fixed live

### Changed

- `lib/use-path-report.ts` (new) — bootstrap + poll `path_report` to
  `'ready'`. Mirrors `identity_report`'s own Tier C bootstrap-then-poll
  shape (`useGenerationStatus` by artifact id, `app/identity/page.tsx`'s
  precedent), not `usePathOptions`/`useCheckpointSessionStatus` — confirmed
  by reading `app/api/path-report/route.ts`'s real response shape first:
  `path_report` is `generating`/`ready`/`failed` (Tier C), not the
  checkpoint-session `generating`/`awaiting_checkpoint`/`complete`
  vocabulary Options uses. Required adding `id` to the GET route's JSON
  response (all three response sites) so the hook can poll by artifact id
  without a second `getCurrentArtifact` round-trip.
- `lib/use-project-naming.ts` (new) — the two-step naming sub-flow
  (generate 3 suggestions via `/api/generate-project-name`, then persist a
  pick/custom name/skip via `/api/name-path-result`) as its own hook,
  deliberately kept separate from `use-path-report.ts`: naming only exists
  once the report is already `ready` and has its own
  loading/submitting/error state with nothing to do with getting the
  report there in the first place. `save()`'s return value is the seam
  back into `use-path-report.ts`'s `setProjectName` setter, since the
  naming hook has no way to reach into the report hook's own state.
- `components/PathReportFlow.tsx` (new) — renders the finished report
  (`thesis`, `what_it_is`, `why_it_fits`, `honest_cost`,
  `life_it_leads_toward`, `master_strategy` as objective cards) plus a
  bottom block pairing naming with a non-functional "what's next" teaser.
  Report sections and the naming dialog markup are recovered from the
  pre-#134 Stage D UI (commit `faedc73`) for the fields/pattern that still
  apply — `not_this`/`plan_seed_actions` are dropped, they don't exist in
  the new schema. Naming is **not** auto-offered on report-ready and **not**
  offered at Options' selection step (both explicitly ruled out this
  session, unlike the old Stage D UI's auto-open-once behavior) — it's the
  one real, working interaction in the bottom block. The teaser has no
  href/onClick: `/plan` still reads the old, orphaned `path_selections`
  table and `/mentor` isn't finished for this flow, so a dead link would be
  worse than plain copy.
- `app/path/page.tsx` — activates `usePathReport`/`useProjectNaming` once
  `options.status === 'complete'` and renders `PathReportFlow`, superseding
  `OptionsFlow`'s own dead-end `'complete'` summary branch the same way
  Slice 1/2 already superseded `DirectionFlow`'s — flagged as unreachable,
  not deleted, same convention.
- **Bug found and fixed**: `lib/path-options-session.ts`
  (`startOrReuseOptionsSession`) and `app/api/path-report/route.ts` (`GET`)
  both inserted a new row unconditionally on every call, only catching
  `23505` for a concurrent-creation race. Both artifacts' unique indexes
  are partial (`WHERE status = 'generating'`), so once a row resolves past
  `'generating'` a fresh insert no longer collides — it silently creates a
  second, empty row that `getCurrentArtifact`'s `created_at DESC` ordering
  then treats as "current," shadowing the real one. Since both bootstrap
  hooks call their GET route on every fresh page mount (not just the
  first), any returning user revisiting `/path` after completing Options or
  generating their report got a blank session/report and a wasted
  regeneration — this blocked Slice 3 entirely, since `path_report` could
  never be reached on any revisit. Found live via this session's own UI
  verification (seeding `path_options_session` already-`'complete'` and
  loading `/path` once reproduces exactly what a real revisit hits — never
  exercised by Slice 2's own live check, which stays in one continuous page
  session and never reloads after reaching `'complete'`). Fixed by checking
  for any existing row first in both places, only falling through to the
  original insert-catch-`23505`-reread path for a genuine concurrent
  first-ever-creation race.
- `scripts/verify-134-slice3-ui.mts` (new) — live-verification script, see
  below.

### Decisions

- `usePathReport` mirrors `identity_report`'s bootstrap-then-poll pattern,
  not `usePathOptions`'s. Why: confirmed via reading the actual GET
  response shape rather than assuming from the task brief's own suggestion
  — `path_report` is genuinely Tier C, not a checkpoint session, so
  `useCheckpointSessionStatus` doesn't apply.
- Naming stays a separate hook from the report's own bootstrap/poll. Why:
  no client-driven mutation of the report's own content exists (no
  refine/select, unlike Options) — naming is the one thing that touches it
  after the fact, and folding its submitting/loading/error state into
  `use-path-report.ts` would mix a concern that only exists post-`ready`
  into a hook whose only other job is getting there.
- Naming trigger point: bottom of the finished report, not on
  report-ready and not at Options' selection step. Why: naming should
  accompany the next real forward step after reading the full report, not
  interrupt generation completion or attach to an earlier, unrelated
  checkpoint.
- Bottom "what's next" CTA is plain copy, no link. Why: `/plan` is
  confirmed orphaned (still reads `path_selections`, the old pre-#134
  table) and `/mentor` isn't finished for this flow — a non-functional or
  misleading link would be worse than an honest "coming soon" teaser.
  `/plan`'s reconnection to `path_report`/`path_options_session` is an
  explicit follow-up, not covered here — needs a real ticket filed, not
  just this note (Definition of Done: a changelog "Next" note alone doesn't
  count as a leftover being taken over).
- Fixed both the `path_options_session` and `path_report` routes' get-or-
  create bug in this same session, rather than just the minimum needed to
  unblock Slice 3's own verification. Why: identical root cause, identical
  fix shape, low risk, no migration needed — leaving the `path_options_session`
  copy of the bug in already-shipped Slice 2 code would have meant knowingly
  shipping a live regression discovered in the course of this same
  investigation.
