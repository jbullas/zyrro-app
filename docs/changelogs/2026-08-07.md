## 2026-08-07 — #103: domain_profile_summary (Layer 2 prose)

Per `docs/briefs/103-domain-profile-summary-brief.md`. Adds Layer 2-generated
prose (~80-110 words) summarizing where a person's strongest patterns
cluster across the five domains, alongside the existing numeric
`domain_profile` radar chart data.

### Changed
- **`lib/artifact-schemas.ts`** — `schema_version` union extended to include
  `"1.3"`. New `domain_profile_summary?: string` added as a top-level
  sibling of `domain_profile` on `IdentitySignatureReportArtifactContent` —
  deliberately not nested inside `domain_profile`, since that object is
  overwritten post-generation by `computeDomainProfile()` in
  `lib/generate-identity-report.ts` and anything nested there would be
  silently lost. Same non-backfill precedent as `#62`'s
  `raw_signature_analysis`: undefined on every report generated before this
  shipped.
- **`lib/prompts/identity-report.ts`** — new `### domain_profile_summary`
  field-requirements section instructing the model to ground the summary in
  which domains the `primary_constellation`/`secondary_signature_analysis`
  entries actually belong to, not in the raw numeric `domain_profile`
  scores (those are recalculated downstream from the Detection Engine's
  real signature scores and can drift from whatever Layer 2 believes while
  writing prose). No signature names (renders before Primary Signatures on
  the page), no redefining the five domains, no repeating
  `cover.identity_thesis`/`constellation_synthesis`. Added to the OUTPUT
  FORMAT JSON template, STRUCTURAL CONSTRAINTS, and the pre-return
  verification checklist.
- **`lib/generate-identity-report.ts`** — no code change. Confirmed the
  existing `report.domain_profile = analysis.domain_profile` defense-in-depth
  overwrite only touches the numeric field, not this one.
- **`app/identity/page.tsx`** — `domain_profile_summary?: string` added to
  the page's report type. Renders as a plain `<p>` (same bare treatment as
  `identity_reframe`'s `recap`) inside the same `.card` as
  `DomainRadarChart`, directly after it — not the `secondary_signature_summary`
  pattern (bare `<p>` outside the card). Guarded with
  `domain_profile_summary &&` for backward compatibility with pre-#103
  reports.

### Verification
- `npx tsc --noEmit` and `npm run build` both clean.
- **Live**, via `withVerificationSession` (ad hoc script in `scripts/`,
  deleted after, not committed):
  - **Real end-to-end generation**: full detection + report generation run
    (~69s) against a synthetic user with real discovery answers.
    `domain_profile_summary` present, 73 words, rendered as the second
    child of `.card` (canvas chart first, `<p>` directly after — confirmed
    by DOM child index, not just presence). No primary signature name
    (`Originator`, `Pioneer`, `Builder`, `Illuminator`, `Contextualiser`)
    appeared in the summary text; no domain-definition language detected.
  - **Backward compatibility**: seeded a legacy-shaped report with
    `domain_profile_summary` omitted entirely. `.card` rendered with exactly
    one child (just the chart) — no empty `<p>`, no console error, no
    layout gap.
- Word count (73) landed a bit under the ~80-110 target on this one sample
  — a single non-deterministic generation, and the prompt explicitly
  prefers a shorter, honest summary over padding, so not treated as a
  defect.

### Decisions
- Followed `#62`'s precedent of bumping the `schema_version` type union
  without touching the prompt's own hardcoded `"schema_version": "1.1"`
  literal in the OUTPUT FORMAT template — the union tracks the artifact
  shape's evolution over time, not a value the LLM is expected to increment
  itself.
