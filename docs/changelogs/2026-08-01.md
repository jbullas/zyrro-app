## 2026-08-01 — #85 tension rule: normalize tense, add evidence-grounding requirement

Per `docs/briefs/85-tension-rule-brief.md`. Originally scoped as a full
rewrite of the Tension Rule's worked examples based on a 2026-07-28 review
finding them "flattering humblebrag"; a real-data check against all 12
real users' current identity_report tension lines (same session) did not
confirm that finding — external triggers (pace mismatches, environment
type) read as legitimate self-located friction, not blame-shifting, once
inspected line by line. Two different, real, evidence-confirmed issues
surfaced instead: tense inconsistency (~10 of 50 real lines definite,

  only: added a requirement that the tension derive from a concrete
  situation in the user's own `evidence_units` rather than generic
  signature-typical phrasing (explicitly allowing two users' genuinely
  similar evidence to produce similar wording — the fix is groundedness,
  not uniqueness); added an explicit conditional-voice (may/might)
  instruction; updated the three worked examples to conditional voice to
  match. No other prompt rule touched.

### Decisions
- No schema change and no `schema_version` bump — `tension` field
  type/length unchanged, consistent with #84/#86/#87 precedent (prompt
  wording changes without a JSON-shape change haven't bumped it; the gap
  in that policy itself is tracked separately under #91).

## 2026-08-01 — Detection Engine determinism investigation (#93, split into #95/#96)

Triggered by observing wildly different Detection Engine (Step A) output
across back-to-back runs against the same stored `discovery_answers` for
two real users, despite `temperature: 0`. Investigated whether this was a
code-path bug (temperature dropped/overridden somewhere before reaching
the API) or an inherent model/provider limitation.

### Investigated
- Read `lib/llm.ts` in full and confirmed `temperature` is forwarded to
  `chat.completions.create()` unchanged via a conditional spread — not
  dropped, defaulted, or overridden anywhere in the adapter or at the
  Detection Engine call site in `lib/generate-identity-report.ts`.
  Model resolves to the hardcoded fallback `gpt-4o` (no `OPENAI_MODEL`
  set in `.env.local`, no other env file present).
- Checked OpenAI's own documentation (cookbook + advanced-usage guide):
  Chat Completions are "non-deterministic by default"; `temperature: 0`
  alone carries no documented determinism guarantee — the mechanism
  OpenAI actually documents for approaching reproducibility is the
  `seed` parameter (which the codebase wasn't passing at all), and even
  with `seed` + matching `system_fingerprint`, OpenAI's own docs say
  "determinism is not guaranteed" and outputs are only "(mostly)
  deterministic."

### Changed
- **`lib/llm.ts`**: added optional `seed?: number` passthrough to
  `getChatCompletion`, same conditional-spread pattern as
  `temperature`/`max_tokens`/`response_format`. Commented as
  OpenAI-specific per `docs/standards/product-decisions.md`'s
  LLM-agnostic requirement — a future non-OpenAI adapter can omit or
  no-op the field without touching the signature or any call site.
- **`lib/generate-identity-report.ts`**: added `seed: 42` to the Step A
  (Detection Engine) call only. Step B (`LAYER_2_PROMPT`) untouched.
- Committed as `1d8b8f6`, after `npx tsc --noEmit` and `npm run build`
  were confirmed clean.

### Verification / measurement
- Read-only, no writes to any table for any of this investigation.
- Measured via 2 real users x 3 back-to-back Detection Engine runs each
  (`miroslav+elias_varga@jeffbullas.com`, `miroslav+helena_ortiz@jeffbullas.com`),
  with `temperature: 0, seed: 42`, against each user's real stored
  `discovery_answers` (confirmed exactly one row per `question_number`,
  no duplicates — `discovery_answers` has no `created_at`/`updated_at`
  columns to independently confirm single-version-ness that way).
- All ad hoc scripts (`scripts/*.ad-hoc.mts`) run and deleted, not
  committed, per each session's confirmation.

### Decisions
- **`seed: 42` did not meaningfully stabilize output.** Elias Varga: 4
  different primary-constellation members appeared across the 3 runs,
  only Architect appeared in all 3, and per-signature scores for the same
  signature still shifted run to run (e.g. Architect 12/16/12). Helena
  Ortiz: primary-constellation membership and per-signature scores also
  varied across all 3 runs (e.g. Builder 16/12/20). Full raw output for
  both users lives in the planning-chat record; the finding itself is
  tracked on the board as ticket **#93, status Dropped, split into #95
  and #96** (further investigation/fix work scoped there, not here).
- **`seed: 42` kept in place regardless** — it's the technically-correct
  parameter to have wired in (OpenAI's own documented, if non-guaranteed,
  determinism mechanism), costs nothing to include, and the `getChatCompletion`
  passthrough itself is inert for any call site that doesn't pass it. Not
  reverted despite not solving the underlying variance.

### Next
- **#95/#96** — own the actual determinism/variance problem surfaced
  here; not resolved by this session's `seed` addition. See ticket #93
  for the full split rationale.
- No further action on `seed` itself pending #95/#96.
