## 2026-09-13 — #141: /api/path-options first-load 403 — root-caused, fixed, live-verified

### Changed

- **Investigation** (first session pass, `docs/briefs/141-path-options-first-load-failure.md`): confirmed all three suspect call sites (`hasEntitlement` in `lib/entitlements.ts`, `loadIdentityReport`/`loadCompletedDirectionContent` in `app/api/path-options/route.ts`, both via `getCurrentArtifact`) destructured only `data` from Supabase and discarded `error` — so the two real-world false-negative-403 incidents were never actually captured anywhere. Added temporary error logging and ran a 20-iteration tight-loop repro (fresh synthetic user each time, seeded entitlement + `identity_report` + complete `path_direction_session`, immediate `GET /api/path-options`) against the real Supabase project via the local dev server: 0/20 anomalies, ruling out a general read-after-write gap or a `.maybeSingle()`-throws-on-2-rows failure (confirmed live: only one `entitlements` row existed for the affected user). No Vercel log access available in this environment, so the session reported honestly that the original incidents' actual error couldn't be recovered from history, and stopped there per the brief's explicit stop condition rather than force-fitting a cause.
- **Root cause** (confirmed via real Vercel/Supabase logs, brought in by the user for the second pass, `docs/briefs/141-fix-retry-on-timeout.md`): the 2026-09-13 incident's `GET /rest/v1/entitlements` returned a real **504** (confirmed in Vercel logs, 08:44:01 UTC) — the only error in 631 Supabase log lines across the incident window, everything else (including the same query seconds before/after) resolving in under a second. Matches a pooled Postgres connection gone idle (a user idling through the three Direction screens) needing to re-establish on its next query. Both real occurrences (2026-09-12, 2026-09-13) were on a first-hit-after-idle-gap and both resolved instantly on an unmodified retry — the tight-loop repro's inability to reproduce is consistent with this, not contradictory to it.
- **Fix**: new `lib/with-db-retry.ts` — `withDbRetry(label, run)` retries a Supabase query exactly once, immediately, only when the result's `status` is `0` (network-level failure — how `@supabase/postgrest-js`'s own fetch `.catch()` reports DNS/connection-reset/abort) or `502`/`503`/`504` (gateway-shaped HTTP failure — confirmed shape for the real 504, read directly from `PostgrestBuilder.ts` rather than assumed). Applied to `hasEntitlement` (`lib/entitlements.ts`) and `getCurrentArtifact` (`lib/artifacts.ts`, refactored to a query-factory closure so a retry fires a genuinely fresh request rather than re-awaiting the same builder instance). `getCurrentArtifact` is shared infrastructure used well beyond this route — extending retry protection to its other callers is treated as a justified side effect of fixing the one shared function, not scope creep, per the brief's own framing; no other call site was touched directly. `/api/path-direction`'s identical-shape check was left alone per the brief (not a trivial shared-helper fit without broader refactoring) — a candidate for a follow-up ticket, not covered here. Kept + un-prefixed the permanent error logging added in the investigation pass; `withDbRetry` itself now logs "retrying" / "recovered" / "did not recover" so a future occurrence reads as clear signal either way.

### Decisions

- Retry is exactly one attempt, immediate, no backoff/loop — the evidence (single 504 in 631 log lines, both real incidents resolved by one plain retry) points at "one idle-reconnect delay," not sustained unavailability, and a heavier retry policy isn't justified by what was actually observed.
- Chose not to touch `/api/path-direction` this session — sharing `withDbRetry` there is a natural fit in principle (identical vulnerability, confirmed in the brief) but doing it properly would mean auditing that route's own call shape rather than a drive-by change; left as an explicit follow-up rather than folding it in.

### Live-verification results

- Project-wide `tsc --noEmit`: clean, no output.
- Forced-failure test (`lib/with-db-retry.ts` exercised directly, 5 scenarios covering: transient-then-success, transient-twice, non-transient, happy-path, network-failure-then-success — 12 assertions): retries exactly once on transient errors and recovers; on two genuine failures, retries once then surfaces the real second error (not masked, not looped); never retries a non-transient error; never retries or adds a call on the happy path. All 12 passed. (Throwaway script, not committed.)
- Live repro against the real dev server (fresh synthetic user, seeded entitlement + `identity_report` + complete `path_direction_session`, real `GET /api/path-options` through actual session cookies): 200, ~2.1s, zero `[db-retry]` log lines — confirms the happy path is unaffected (no added latency, no spurious retry).
- Did not attempt a genuine idle-gap repro (seed then wait several minutes with no DB activity) this session — the brief flagged this may not reproduce on demand regardless; the forced-failure test plus the confirmed-shape live logs were treated as sufficient verification for this fix.

## 2026-09-13 — #143: Options step inline select/confirm UX — fixed, live-verified

### Changed

- **`components/OptionsFlow.tsx`** (`docs/briefs/143-options-select-confirm-ux.md`): the comment textarea + Confirm/Change-selection controls used to render in a separate card below all four candidates, disconnected from which one was actually selected — confirmed via live testing to read as broken (Confirm visually nested inside the "ANYTHING ELSE?" box, as if commenting were required to proceed). Replaced the `SecondaryButton` select control with a checkbox-style toggle (`.option-select-toggle`, styled with the existing `.btn-link` brand color `var(--color-grad-2)` via `accent-color` — no new color token); checking selects, unchecking deselects, no separate "Change selection" control. Comment textarea + Confirm now render inline inside the selected candidate's own `ConstellationCard`, not a bottom-of-page card. `comments` (single shared string) replaced with `commentsByCandidate`, a `Record<string, string>` keyed by candidate id and owned at the `OptionsFlow` parent level — deliberately, so comment text survives regardless of future card-markup restructuring, per the brief's own reasoning. Confirm selection is now a `PrimaryButton`, a deliberate exception to this flow's otherwise-consistent Secondary-for-progression pattern (Direction's three Continue buttons stay Secondary, untouched) — Confirm is the only `/path` action that triggers real report generation (an LLM call and cost), not just navigation.
- **`docs/standards/branding-guidelines.md`**: recorded the Confirm-selection-is-Primary exception under the Buttons section's "Secondary / Transactional" entry, explicitly for #137 — so a future button-consistency pass doesn't "correct" it back to Secondary without knowing why it's intentionally different.
- **`app/globals.css`**: two new classes, `.option-select-toggle` and `.option-card-confirm`, added next to the existing `.option-card-footer` block.
- Scoped exactly per the brief: `DirectionFlow.tsx` and the route/API layer (`lib/use-path-options.ts`'s `submitSelect` contract) untouched — confirmed via `git status`/`git diff` throughout.

### Decisions

- No new color token — the checkbox's checked-state color reuses `var(--color-grad-2)` via the CSS `accent-color` property, the same value `.btn-link` already uses.
- `commentsByCandidate` lives in the parent (`OptionsFlow`), not in any per-candidate sub-component, specifically so a future restructuring of the card markup (e.g. sub-components, collapsed/hidden unselected cards) can't accidentally lose comment text by unmounting the card it used to live in.

### Live-verification results
