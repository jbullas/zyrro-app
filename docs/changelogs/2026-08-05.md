  production build) ran against the same `.next` output directory that
  `npm run dev` then started against afterward. The on-disk chunk file
  `.next/dev/static/chunks/app_globals_0jn8.0u.css` had a stale mtime

  the mid-session `npm run build` and the subsequent clean process
  restart — Turbopack reused the cached chunk rather than recompiling it,
  and a plain process restart alone does not invalidate that on-disk
  cache.
- **Fix**: deleted the entire `.next` directory (confirmed safe —
  gitignored build output, fully regenerated from source) and started
  `npm run dev` fresh. Confirmed via direct `curl` of the served CSS
  chunk that the new colors/classes were present before re-running any
  verification.
- **For future sessions**: if a live-verification check shows CSS/behavior
  that doesn't match a just-made source edit, and a plain dev-server
  restart doesn't fix it, suspect a stale `.next` cache before suspecting
  the browser or the edit itself — especially if `npm run build` and
  `npm run dev` both ran against the same `.next` directory earlier in the
  session. `rm -rf .next` + fresh `npm run dev` is the reliable fix; don't
  assume a restart alone cleared it without re-confirming via a direct
