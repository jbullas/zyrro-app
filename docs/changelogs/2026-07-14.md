- Added `allowImportingTsExtensions: true` to `tsconfig.json` — required for
  `run-verification.mts` to import its sibling `.mts` modules by literal
  extension under this project's `moduleResolution: "bundler"` setting,
  which doesn't support extensionless or `.js`-suffixed resolution of `.mts`
  targets the way `node16`/`nodenext` do.
- Two real bugs found and fixed while live-testing the pipeline (not just
  typechecked — ran `--selftest` and `--selftest-fail` against the dev
  server, screenshotted the rendered report, and independently re-queried
  Supabase afterward to confirm no orphaned rows across all five tables for
  all four synthetic test users created during the session):
  1. `seedArtifact` for `type: 'identity_report'` collided with the
     `artifacts_one_identity_report_per_user` unique index, because hitting
     `/auth/callback` for a brand-new user fires `kickoffIdentityGeneration()`
     in the background, which inserts its own `generating` identity_report
     row a few hundred ms before the seed call runs. Fixed by deleting any
     existing identity_report row for the user before inserting the seeded
     one.
  2. The self-test's happy path timed out waiting for `.report-cover`
     because `app/identity/page.tsx` gates on having at least one
     `discovery_answers` row before it will look at the artifact at all —
     added `seedDiscoveryAnswers` (schema confirmed from the working insert
     in `lib/kickoff-identity-generation.ts`, since `discovery_answers` has
     no tracked migration) and wired it into the context.

### Decisions
- The `kickoffIdentityGeneration` race above is a test-script quirk, not a
  product-level bug — production's kickoff path already guards genuine
  concurrent-`/auth/callback` races (double-click, retry) via its
  existing-artifact check plus a swallowed unique-index error on the losing
  insert. No real user flow seeds a second identity_report immediately
  after signup the way this tooling deliberately does, so no ticket opened
  for it.
- Quick gate pass on `/path`, `/plan`, `/mentor` for future callers of this
  skill: `/path` has no hard gate (OPEN_ACCESS bypasses entitlements) but
  will auto-trigger a **real** call to `/api/generate-path-options` if no
  `path_options` artifact exists yet — same side-effect category as
  identity's background kickoff. `/plan` requires a `path_selections` row
  (`path_options_artifact_id` + `path_id`) in addition to the `path_plan`
  artifact itself — not covered by any seed helper yet. `/mentor` has no
  artifact gate, just needs the authenticated session bootstrapTestUser
  already provides. Noting these here rather than solving them now, so
  they're not silently rediscovered later.

### Next

  helper to `scripts/verification/session.mts` first.

## 2026-07-14 — session 3: #33 signature ordering + #1 domain_profile

### Changed
- Implemented ticket #33: `sortByScoreDescending()` in
  `lib/generate-identity-report.ts` sorts `report.primary_constellation` and
  `report.secondary_signature_analysis` by score descending after Layer 2's
  JSON is parsed, since the detection prompt's "rank by score" rule governs
  Top-5 *selection*, not guaranteed output array order.
- Implemented ticket #1: `computeDomainProfile()` derives `domain_profile`
  deterministically from the Detection Engine's real per-signature scores
  (max score per domain, scaled 0-100, floored at 10), replacing the LLM's
  own disconnected `domain_profile` judgment that caused the reported
  Connecting/Driving inversion. Overwritten once after Step A (so Layer 2's
  "copy from detection JSON" instruction copies a grounded number) and again
  after Step B as defense in depth.
- Verified #1's open question directly against a real generation rather than
  guessing: the Detection Engine's `signatures` array contains **only**
  signatures with actual detected evidence (5 of 25 in the test run) — never
  all 25 with `score: 0` placeholders, and domains with zero evidence are
  simply absent from the array. This is why `computeDomainProfile` treats
  "absent from the array" and "floored" as the same case — there's no way to
  positively distinguish confirmed-zero evidence from evidence too weak to
  report.
- Ran an 8-angle parallel code review (correctness × 3, reuse, simplification,
  efficiency, altitude, conventions) against the initial diff before
  finalizing. Confirmed findings folded in:
  - Domain-floor inversion: a real but weak signature (score 1-2) computed to
    4-8, *below* the floor of 10 used for domains with zero evidence —
    inverting the floor's intended meaning. Fixed by clamping with
    `Math.max(DOMAIN_FLOOR, scaled)` in addition to `Math.min(100, ...)`.
  - `computeDomainProfile`/`sortByScoreDescending` now guard against
    non-array input and non-finite scores (defensive at this boundary since
    LLM JSON output is external, untrusted input, unlike the rest of this
    file's internal state) instead of throwing and failing generation outright
    on a malformed LLM response — a new failure mode the original diff would
    have introduced.
  - Extended the #33 sort to `report.signature_profile_summary.primary_signatures`
    /`secondary_signatures` — same `{name, score}` shape, same unordered-array
    risk, and confirmed via `app/api/mentor/route.ts:42` that it's read in
    array order into the mentor's context prompt. Not named in the brief, but
    the identical bug class per the brief's own precedent (it already
    extended the fix to `secondary_signature_analysis` "even though it wasn't
    named in the ticket"). Consistency-swept the rest of the app first
    (`path-plan.ts`/`path-options.ts` treat `primary_constellation` as an
    unordered set; dashboard/conversation-bundle/meta-bundle have no
    references at all) — confirmed these two are the only real consumers.
  - `computeDomainProfile` now returns `lib/artifact-schemas.ts`'s
    `DomainProfile` type instead of a redundant parallel `Record<Domain, number>`.
- Extended `scripts/verification/session.mts`'s `bootstrapTestUser` with an
  optional `metadata` param (passed to `generateLink`'s `options.data`, i.e.
  the new user's `user_metadata`) so a live-verification pass can fire a
  **real** `generateIdentityReport` run through `kickoffIdentityGeneration`
  end-to-end, not just seed a final artifact. Used this to live-verify both
  fixes against one real two-step LLM generation (in addition to a direct
  function-level test against #1's literal reported regression case:
  Amplifier/Connecting 25 vs Builder/Driving 16) — confirmed sorted arrays,
  correct domain_profile, and a coherent rendered report ("Strategic System
  Architect... you build resilient systems by diving deep and optimizing
  relentlessly," matching the sorted Builder/Depth Diver/Optimizer
  signatures). Independently re-queried Supabase afterward to confirm no
  orphaned rows from the synthetic test user.
- Split the combined working-tree diff into the two requested separate
  commits (070b4b8 for #33, b7164a8 for #1) via `git add -p`, using a
  scripted `$GIT_EDITOR` for the two hunks where the #33 and #1 changes were
  fully contiguous insertions with no unchanged lines to split on — confirmed
  the exact keep/drop split in plain text before writing or running anything,
  and confirmed the script's behavior against that text before it touched the
  real `git add -p` session. Working tree file was never rewritten; only the
  index was touched.

### Decisions
- Known, un-fixed findings flagged rather than silently decided or expanded
  into scope:
  - `signature_number` fields ("01"-"05"/"06"-"08") aren't renumbered after
    the sort, so an entry's own field can point to a different rank than its
    post-sort array position. Currently dormant — `app/identity/page.tsx`
    renders `i + 1`/`i + 6` from array index, never reads `signature_number`
    — but it's persisted stale into the DB. Out of the brief's explicit scope
    (sort the array, not renumber fields); latent follow-up if a future
    consumer starts reading that field directly.
  - Tie-break/missing-score behavior: no ties or missing scores observed in
    practice, but `sortByScoreDescending` makes an explicit choice — missing/
    non-numeric scores sink to the bottom (`-Infinity`) rather than producing
    `NaN`; genuine ties keep their original relative order (stable sort).
  - The Detection/Layer-2 prompts still ask the LLM to invent and self-verify
    `domain_profile`, even though the value is now fully discarded by code —
    wasted generation budget on every run. Brief #1 explicitly scoped out
    prompt changes, so left alone; worth a separate ticket to reclaim the
    tokens.
- `docs/briefs/33-primary-signature-ordering.md` and
  `docs/briefs/1-domain-profile-computed.md` are fully implemented and
  verified; ready to be deleted as shipped in a future cleanup pass (same
  pattern as #49's brief).
