## 2026-08-10 — #110: Detection Engine full signatures[] + code-computed Primary/Secondary

Per `docs/briefs/110-detection-categorization-brief.md`. Two related
Detection Engine (Layer 1) defects: `signatures[]` had no completeness
rule in the prompt, so in practice it matched `primary_constellation` 1:1
instead of listing every detected signature; and Primary/Secondary
categorization trusted Layer 1's own `primary_constellation`/
`secondary_signatures` name-array judgment instead of the actual `score`
values, so Secondary could legitimately outscore Primary.

### Changed
- **`lib/prompts/identity-analysis.ts`** (`DETECTION_PROMPT`) — new SCHEMA
  RULES line: `"signatures"` must include every signature with at least 1
  evidence unit anywhere in the narrative, not only the Top 5.
  `primary_constellation`/`secondary_signatures` remain a *selection* from
  that list, not a filter on it. `HARD CONSTRAINTS` (minimum 2 evidence
  units per strong signature) untouched — governs Primary/Secondary
  eligibility, not `signatures[]` membership.
- **`lib/generate-identity-report.ts`** — new exported
  `categorizePrimarySecondary(signatures)`: sorts by score descending,
  returns `{ primary: top 5, secondary: positions 6-8 }`. Called in Step A
  right after `computeDomainProfile`, overwriting
  `analysis.primary_constellation`/`secondary_signatures` before Layer 2
  runs — same "overwrite before Layer 2 sees it" pattern already
  established for `domain_profile`. New `logCategorizationComplianceGaps`
  (log-only, not exported outside this module in the shipped version),

Two live-verification rounds were needed because the first attempt
produced an unexpected regression — recorded here in full rather than

**Round 1 (rejected after live verification):** Set `evidence_analysis` to
a bare `"140–160 words."` and `how_you_operate` to a bare `"120–150

diagnosed as caused by dropping the minimum/target framing itself, not by
the new lower numbers — the bare range read to the model as an upper
bound to respect rather than a target to reach.

**Round 2 (shipped):** Reverted `evidence_analysis` to `"minimum 140
words, target 160 words."` and `how_you_operate` to `"Each minimum 120
words, target 150 words."` — same new numbers, old framing style. Re-ran

for evidence_analysis, 109/120 for how_you_operate). Logged as the honest,
expected result per Miroslav's explicit framing going in ("this is not
expected to achieve full compliance... the point of this revert is that
minimum language empirically pulls output higher, not that it solves the
shortfall outright") — not iterated on further this session.

`domain_profile_summary` kept its "90–120 words, loose guide — content
quality and relevance matter more than hitting an exact count" framing
throughout both rounds (the softer framing was judged correctly targeted

Same 3 personas every round, same mechanical-overlap measurement, real

### Decisions

- **Item 1 (recap↔thesis/synthesis overlap) is a logged, accepted gap,
  not a fix.** None of the 3 rounds solved it — Priya's exact opening
  clause reproduced identically across all four measurements regardless
  of which prompt variant was tried. Per Definition of Done, this is
  explicitly accepted as an untested/unresolved gap rather than silently
  shipped as if solved: the prompt-level instruction reduces neither the
  frequency nor the severity of this specific failure in any
  statistically meaningful way this session demonstrated. **The
  code-level `logReframeTeaserRecapOverlap` backstop is the actual
  reliable safety net going forward** — it does not prevent the
  repetition, but it has proven, across every round, that it will always
  surface it for review when it happens in production.
- **R3's recap instruction (check every sentence, not just the first) is
  kept on disk despite not producing the best measured numbers.** Its
  Round 3 average (77.3) was worse than Round 1's (64.3). This is kept
  anyway because it is the more *complete* rule — Round 1's original
  version and Round 2's replacement both only implicitly or explicitly
  constrained the first sentence, and the investigation directly proved
  (Priya's second-sentence verbatim duplicate) that later-sentence
  duplication is a real, distinct failure mode the earlier versions never
  addressed at all. The Round 3 regression on Dana specifically is
  attributed to likely generation noise rather than the instruction being
  actively harmful: between-round swings of this magnitude on personas
  *not* targeted by a given round's specific change (e.g. Marcus's
  167→84 swing between Round 2 and Round 3, when nothing in Round 3 was
  aimed at Marcus's specific failure) were observed throughout this
  investigation and were never fully explained by the prompt text alone
  — real generation at temperature 0 was shown elsewhere this session to
  still carry meaningful run-to-run variance (Marcus's own
  `identity_thesis` wording differed between Part A's baseline run and
  Round 1's run despite identical prompt input). Keeping the more
  complete rule on a plausible-noise data point is judged better than
  reverting to a version already proven to have a known, demonstrated
  blind spot. This is a judgment call, logged explicitly as one, not
  presented as proven.
- **Item 4 (filler-phrase banning) will not be re-attempted with a
  different wording in a future session expecting a different result.**
  3 independent attempts — the original Tier-1 list (Round 1), a general
  "avoid this shape" structural ban (Round 2), and reverting back to the
  Tier-1 list (Round 3) — each produced measurable suppression of the
  specific phrase(s) targeted, and each time the model substituted a
  *different*, previously-unbanned filler phrase instead (`"as you prefer
  to"` → `"This matters because it..."` → `"is not just about..., it's
  about..."`, plus repeated reappearances of already-"banned" phrases
  across rounds). This is concluded to be **structural to how this model
  writes under these constraints** (Pattern → Evidence → Meaning
  structure, word-count targets, "must use recurrence language" from THE
  REPETITION RULE), not a wording problem solvable by a better-phrased
  ban. Flagged explicitly so a future session doesn't re-spend rounds on
  the same phrase-banning strategy expecting a different outcome — a
  different lever (e.g. code-level detection/logging, similar to
  `logReframeTeaserRecapOverlap`, or accepting connective filler as an
  inherent stylistic cost) would need to be tried instead.
