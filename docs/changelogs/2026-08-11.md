### Stage 0 — Evidence data audit

**Premise correction (the actual headline finding of this stage).** The
brief's data source — "`evidence_units` and `signatures[]` already
persisted on `identity_report` artifacts since #62 shipped" — is only
half true. Queried live Supabase directly (23 `identity_report` artifacts,
8 with `raw_signature_analysis` present, all from 2026-08-04 onward):

```
Artifacts with raw_signature_analysis present: 8
Of those, raw_signature_analysis containing an 'evidence_units' key: 0
Of those, raw_signature_analysis.signatures non-empty array: 8
Artifacts with top-level content.evidence_units key: 0

raw_signature_analysis keys: [
  'signatures', 'emerging_signatures', 'secondary_signatures',
  'primary_constellation', 'suppressed_signatures'
]
```

`evidence_units` was never actually persisted — `#62`'s scope, as
actually shipped in `lib/generate-identity-report.ts:590-596` and typed in
`lib/artifact-schemas.ts:176-182`, only ever wrote the full `signatures[]`
array plus the four categorization lists (`primary_constellation`,
`secondary_signatures`, `emerging_signatures`, `suppressed_signatures`).
Layer 1 generates `evidence_units` transiently every run but it's
discarded before the `artifacts.content` write — it never reaches the DB.
Confirmed no separate artifact type carries it either: the only `type`
values present in the live `artifacts` table are `identity_reframe`,
`identity_report`, `path_options`, `path_plan` — no `signature_analysis`
type (the `SignatureAnalysisArtifactContent` type in
`artifact-schemas.ts:56-76` that does declare `evidence_units` describes a
shape nothing in the app actually writes).

**Practical effect:** measures 1, 2, and 4 (all keyed on `evidence_units`
grouped by `source_question`) are not answerable from historical data —
not a weak signal, a hard zero across every real report generated to
date. Per Miroslav's direction, these were folded into Stage 1's
verification pass instead (see below) rather than dropped, since Stage 1
generates fresh `evidence_units` against the same real users' real
`discovery_answers` anyway.

**Measure 3 — evidence density per signature by `score_band`.** This one
*is* answerable — `signatures[].evidence_count` is real, persisted data,
independent of the missing `evidence_units` array. All 8 artifacts, 43
signature entries:

```
weak      : n=8,  avg=1.00, min=1, max=1,  values=[1, 1, 1, 1, 1, 1, 1, 1]
moderate  : n=16, avg=2.50, min=2, max=5,  values=[2, 5, 2, 2, 2, 2, 2, 2, 3, 2, 2, 2, 2, 4, 3, 3]
strong    : n=12, avg=4.00, min=3, max=7,  values=[3, 7, 5, 3, 4, 3, 3, 3, 3, 5, 4, 5]
dominant  : n=7,  avg=5.86, min=4, max=10, values=[5, 5, 10, 6, 6, 5, 4]
```

Clean, monotonic, low-noise relationship (`weak` has *zero* variance — every
single weak-band signature in the real data has exactly 1 evidence unit,
n=8). This is the number the brief asked for: a weak-band signature is
backed by exactly 1 evidence unit, on average less than half of what a
moderate-band signature has (2.5) and roughly a sixth of a dominant-band
signature (5.86). Directly explains why word-count floors requiring
"minimum 2 real story details" (per `evidence_analysis`'s existing prompt
rule) are structurally unachievable-without-padding for weak-band
signatures specifically — there is often only 1 real detail available to
cite, confirmed by real data, not inferred.

### Stage 1 — Detection Engine v2 (standalone)

**Shipped, not wired in:** `lib/detection-engine-v2.ts` — `DETECTION_PROMPT_V2`
(new prompt, evidence-extraction scope only — deliberately narrower than
the live `DETECTION_PROMPT`, since `signatures[]`/`primary_constellation`/
`named_identity`/`domain_profile` are out of scope for this stage; those
become entirely code-computed from `evidence_units` downstream under this
design) and `computeSignatureScoresFromEvidenceUnits()` (the
Frequency/Intensity/Score formula from the brief, implemented exactly as
specified: Frequency = distinct `source_question` count capped at 5,
Intensity = max of Strong=5/Normal=3/Weak=1 across a signature's links,
Score = Frequency × Intensity). Nothing in `lib/generate-identity-report.ts`,
`lib/prompts/identity-analysis.ts`, or any API route imports or calls this
module. `npx tsc --noEmit` clean.

**Test method:** 6 real personas, all pre-existing in the DB with real
`discovery_answers` (13/13 each) and a real prior `identity_report`
generation to compare against — chosen for domain/score-band spread from
the 8 real users found in Stage 0's audit (`domain_profile` from their
existing reports): `katalin_farkas` and `matteo_varga` (Visioning-top, no
dominant-band signature), `nadia_petrescu` (Driving-top + high Sensing,
has dominant-band signatures), `tomasz_zielinski` (Driving specialist,
Thinking=10, has dominant), `leona_markovic` (Driving/Thinking balanced,
no dominant-band signature), `ingrid_solberg` (Driving/Thinking balanced,
has dominant-band signatures). Real OpenAI calls throughout
(`temperature: 0, seed: 42`, same as the live pipeline's Layer 1 call),
no mocking. 6 first-pass generations (one per persona) plus 6 more from
the rerun-stability check below — 12 real generations total this stage.

#### 1. Lens differentiation — PASS, but on a thin sample

Across all 6 personas' first-pass runs, only **2 of 77** evidence units
(2.6%) received 2+ signature links at all:

```
matteo_varga Q2: "I was mostly responsible for finding opportunities,
negotiating difficult acquisitions and getting complicated projects
moving."
  -> Activator [Normal]: Focus on initiating and driving projects forward.
  -> Pioneer [Normal]: Explores new paths by finding opportunities and
     negotiating acquisitions.

tomasz_zielinski Q2: "I led a temporary crisis unit rerouting cargo
across several countries."
  -> Pioneer [Normal]: Demonstrates exploring new paths and handling
     uncertainty.
  -> Activator [Normal]: Indicates moving to action quickly in a crisis
     situation.
```

Both genuinely distinct — one lens reads "initiates/drives," the other
reads "explores under uncertainty"; not a reworded duplicate in either
case. No near-duplicates found. But the real finding here is the
denominator: the schema's "no cap on links, link whatever the evidence
genuinely supports" design is barely exercised in practice — the model
defaults overwhelmingly to single-signature linking (avg 1.00–1.09
links/unit per persona, identical pattern held across all 6 rerun-stability
generations in section 5 below). This is the opposite of the brief's
anticipated failure mode (uniform *high* link counts / hedging) — the
real risk observed is the model barely using multi-linking at all, not
overusing it.

#### 2. Relevance calibration — real, confirmed miscalibration on the Weak band

Aggregate across all 6 personas' first-pass runs (79 total links):

```
Strong: 28/79 (35.4%)
Normal: 51/79 (64.6%)
Weak:    0/79 (0.0%)
```

Strong is not the dominant band (the brief's specifically-named failure
mode — "if most links end up Strong" — did not occur; Normal correctly
dominates, matching "most real evidence should land on Normal"). But
**Weak was never used once**, in any of the 6 personas' first-pass runs.
The rerun-stability check (section 5) adds 6 more independent real
generations across 3 of those personas — still 0 Weak links, out of
those 6 additional runs. This is not a one-off: 12 independent real
generations total, 0 Weak links. The model is not using the full 3-band
scale specified verbatim in the prompt; it collapses to an effective
Strong/Normal binary.

**Per this session's explicit standard, this is reported plainly as a
real, confirmed failure of the relevance-calibration verbatim wording as
specified — not iterated on with a fourth prompt variant this session.**

#### 3. Link count / hedging — no hedging observed, but see item 1

Per-persona average links/evidence-unit, first pass: katalin 1.00, matteo
1.07, nadia 1.00, tomasz 1.09, leona 1.00, ingrid 1.00. No sign of
uniform high link counts anywhere — if anything, the opposite (item 1).
Max links on any single unit, across all 6 personas' first-pass runs and
all 6 rerun-stability runs: 2. No hedging risk observed in this data.

Top-3-by-score overlap between v2's code-computed ranking and each

| katalin_farkas | Architect(15), Builder(15), Alchemist(10) | Alchemist(16), Optimizer(9), Builder(6) | 2/3 |
| matteo_varga | Builder(25), Visionary(15), Activator(9) | Originator(16), Builder(12), Architect(6) | 1/3 |

Notable wild divergence: katalin_farkas's v2 run scores Architect at 15

— but Architect doesn't appear anywhere in her real v1 signature list at

**Important caveat on this comparison, stated plainly rather than glossed
over:** this does not isolate the scoring *formula* from the *evidence
extraction* — v1 and v2 are different prompts run independently, so a
divergence can come from v2 extracting/linking evidence differently, not
just scoring it differently. A cleaner test (code-computed formula
applied to the *same* evidence set the live pipeline used) isn't possible
because Stage 0 confirmed that evidence set was never persisted. Given
that caveat, rankings show partial but inconsistent agreement — not the
"broadly agree" bar the brief was checking for, and not a clean pass
either.

3 personas (katalin_farkas, matteo_varga, tomasz_zielinski), 2 additional

6 new generations this check specifically — same input, `temperature: 0,

matteo_varga's case, more severe than #93's original finding — a
signature (Architect) going from entirely absent to tied-for-top and back

across 3 identical-input runs at `temperature: 0`.

#### Q11/Q12 concentration checks (Stage 0 measures 1 & 2, folded in per Miroslav's direction — run against Stage 1's freshly-generated real `evidence_units` instead of historical data, since none exists)

**Measure 1 — volume distribution by `source_question`:** NOT
concentrated in Q11/12. Summed across all 6 personas' first-pass runs (77
evidence units total): Q11 and Q12 combined account for 11/77 (14.3%) —
essentially the even-distribution baseline for 2 of 13 questions (15.4%),
slightly *under* it. Q4 was the single busiest question (10/77, 13.0%),
matching its "energy + frustration" weighting-rule role. Q8 and Q10 were
the least-cited (2/77 each).

**Measure 2 — `emotional_weight` disproportionately high for Q11/12:**
YES, confirmed, cleanly. Every evidence unit sourced from Q11 or Q12
across all 6 personas was tagged `emotional_weight: "high"` — 11/11
(100%), zero exceptions. Baseline `high` rate across all 77 evidence
units, all 13 questions: 31/77 (40.3%). Q11/12 evidence is tagged high
2.5× more often than the all-question baseline, with no noise in the
signal (11/11, not e.g. 9/11). This is a direct, real confirmation of
#112's original root-hypothesis half — and it's not a rogue extraction
bias, it's the prompt working exactly as designed:
`DETECTION_PROMPT_V2`'s (and the live `DETECTION_PROMPT`'s, unchanged)
own explicit instruction is "Q11-12 = strongest intensity signals" /
"Q11-12 must strongly influence intensity scoring." Combined with the new
code-computed Intensity formula (max relevance across a signature's
links), a signature whose only strong link happens to come from Q11/12
will reliably hit Intensity=5 by design, not by accident.

**Measure 4 — does generated prose disproportionately cite Q11/12
material:** still unanswerable this stage. This measure is about Layer
2's *prose* (`evidence_analysis`, `how_you_operate`, reframe bullets) —
Stage 1 only produces `evidence_units`, no narrative generation (Call 2 is
explicitly out of scope for this brief). Deferred to the Call 2 pilot

### Recommendation

**Do not proceed to the Call 2 pilot with Stage 1's schema/formula as-is.**
Two real, confirmed findings meet this session's explicit "stop and report
plainly" bar rather than being iterated past:

1. Relevance calibration never uses the Weak band — 0/79 first-pass links,
   0/additional-stability-run links, 12 independent real generations
   total, 0 Weak. The 3-band scale specified verbatim in the prompt
   collapses to a 2-band scale in practice.
2. Run-to-run instability is real and, in at least one case
   (matteo_varga), more severe than #93's original finding — not just
   score magnitude drifting, but which signatures appear in the list at
   all changing between identical-input runs.

Item 4 (score sanity vs. old model-asserted scores) is a secondary,
softer finding given the stated comparison caveat, and would likely
improve somewhat once items 1 and 2 are addressed — not treated as
independently disqualifying, but not evidence of health either. Item 1
(lens differentiation) and item 3 (link count/hedging) are genuine,
clean passes, with the caveat that multi-linking is exercised too rarely
(2.6% of evidence units) to be confident the "no near-duplicate lenses"
result generalizes to a persona whose narrative genuinely produces more
cross-signature evidence.

The code itself (`lib/detection-engine-v2.ts`) is sound and kept on disk
as the standalone deliverable this brief asked for — the formula
implementation matches the brief's spec exactly and the module is fully
isolated from the live pipeline. What's not ready is the *prompt*
driving it (Weak-band calibration) and an open question about whether
Layer 1's underlying non-determinism (item 5) is something a scoring
redesign can route around at all, or whether it's a ceiling on how
reliable any Detection Engine v2 formula can be regardless of prompt
wording.
