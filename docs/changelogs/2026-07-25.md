## 2026-07-25 — #72 retry-generation DB fallback for State-3 users

### Changed
- **`lib/kickoff-identity-generation.ts`**: when `rawAnswers.length === 0`
  (no `user_metadata.discovery_answers`), after the existing `profiles`
  upsert now queries `discovery_answers` for `user.id` (ordered by
  `question_number`) before giving up. Zero DB rows → unchanged `return
  false`, no artifact. One or more rows → mapped into `DiscoveryAnswer[]`
  and passed to `completeDiscovery(user.id, answers, name)`, same as the
  metadata path. Closes the gap flagged during #20's 2026-07-23 session 2
  (that entry's Decisions section) — a State-3 user (answers submitted via
  `POST /api/complete-discovery` while already authenticated) never has
  metadata answers, so `/identity`'s "Try again" → `POST
  /api/retry-generation` → `kickoffIdentityGeneration` used to silently
  no-op forever for them even with real `discovery_answers` rows on file.
- Did not touch `completeDiscovery`, `/api/complete-discovery`, or the
  retry-generation route/UI — per the brief's explicit stop conditions.

### Decisions
- **Extracted the metadata-row-to-`DiscoveryAnswer[]` mapping into a small
  private `toDiscoveryAnswers()` helper inside
  `lib/kickoff-identity-generation.ts`**, used by both the existing
  metadata path and the new DB-fallback path. Took the brief's offered
  option rather than inlining a second copy: same file, same shape on both
  sides (`question_number`/`answer_text` in, `DiscoveryAnswer[]` with
  `question_text` joined from `QUESTIONS` out), no import-cycle risk since
  it doesn't leave the file `DiscoveryAnswer` isn't already imported into.
