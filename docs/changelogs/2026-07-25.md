## 2026-07-25 — session 2: #71 make path_options/path_plan append-only

### Changed
- **`lib/artifacts.ts`**: extended `getCurrentArtifact` with an optional
  `opts.match: Record<string, string>` — extra equality filters beyond
  `user_id`+`type`, applied via `.match()` before the existing
  `.order('created_at', { ascending: false }).limit(1)`. Purely additive;
  existing callers (`identity_report`, `path_options` reads) pass no `match`
  and are unaffected. This is the one shared place all four `path_plan`
  selection-scoped lookups now route through.
- **`app/api/generate-path-options/route.ts`**: removed the
  `if (existing) UPDATE else INSERT` branch. Now always INSERTs a new
  `path_options` row — regeneration never destroys history. Before
  inserting, deletes any `failed` `path_options` row for the user (see
  Decisions).
- **`lib/generate-path-plan.ts`**: replaced the bare `.maybeSingle()`
  existing-check (no ordering, would throw once a second row can exist)
  with `getCurrentArtifact(..., { match: { path_options_artifact_id,
  path_id } })`. `generating`/`ready` current row → return its id unchanged.
  `failed`/no row → delete failed rows for that selection key, then INSERT
  a fresh row (replacing the old "UPDATE the failed row back to
  generating" branch).
- **Read-site migration onto the extended `getCurrentArtifact`** (all four
  `path_plan` selection-scoped lookups the brief called out):
  `app/api/select-path/route.ts`'s `existingPlan` lookup (status: `ready`
  kept), `lib/generate-path-plan.ts`'s own existing-check (covered above,
  no status filter), `app/plan/page.tsx`'s `loadPlanArtifact` (no status
  filter — `useGenerationStatus` handles whatever phase it's in), and
  `app/api/mentor/route.ts`'s `planArtifact` lookup (status: `ready` kept).
- **New migration** `20260725000000_path_options_path_plan_unique_indexes.sql`
  — see Decisions (scope growth beyond the original brief). Applied live by
  the user in the Supabase SQL Editor and re-confirmed via `pg_indexes`:
  both `artifacts_one_path_options_generating_per_user` (`ON (user_id)
  WHERE type = 'path_options' AND status = 'generating'`) and
  `artifacts_one_path_plan_generating_per_selection` (`ON (user_id,
  path_options_artifact_id, path_id) WHERE type = 'path_plan' AND status =
  'generating'`) confirmed present with the expected definitions before any
  code depending on them was exercised live.
- **Lost-race handling** in both `generate-path-options/route.ts` and
  `generate-path-plan.ts`: on an insert `error.code === '23505'` (unique
  violation against the new indexes), re-resolve the current row via
  `getCurrentArtifact` (no status filter — the winner's row is guaranteed
  newest regardless of what it's since resolved to) and return/hand back
  *that* row's id instead of erroring. Not touched: `identity_report`'s
  handling, `generate-project-name`'s primary-key lookup, any UI beyond the
  backend behavior.

### Decisions
- **Delete failed rows before inserting, for both `path_options` and
  `path_plan`** — matching #59's `kickoffIdentityGeneration` precedent (a
  `failed` row has no informational content). Applied consistently: a
  blanket delete scoped to `user_id`+`type`(+`path_options_artifact_id`+
  `path_id` for `path_plan`)+`status = 'failed'`, run unconditionally before
  every insert, not conditioned on which specific row was "current."
- **Scope grew beyond the original #71 brief: added two partial unique
  indexes that the brief never mentioned.** Caught during review, not in
  the brief's Scope section (1–4) — removing `generate-path-options`'s
  "if existing, UPDATE" branch also removed the incidental protection that
  branch gave against concurrent double-inserts (double-click,
  retry-after-slow-response) for a user who already had a `path_options`
  row. Checked live migrations first: no unique index has ever existed for
  `path_options` or `path_plan` (both explicitly called out as unaffected
  in `20260622000000_artifacts_identity_report_unique_index.sql`'s and
  #59's narrowing migration's own comments) — so this wasn't a
  regression the brief could have assumed away, it was a real gap #71's
  write-path rewrite would have reopened. Chose to close it the same way
  #59 closed it for `identity_report`: a partial unique index scoped to
  `status = 'generating'`, applied live and confirmed via `pg_indexes`
  before writing any code that depends on it.
- **Did not add a `CHECK` constraint enforcing `path_options_artifact_id`/
  `path_id` non-null when `type = 'path_plan'`.** The path_plan composite
  index's uniqueness guarantee technically doesn't hold against `NULL`
  values (Postgres treats `NULL`s as distinct in unique indexes), but
  confirmed there is exactly one insert site for `type: 'path_plan'` in the
  whole codebase (`lib/generate-path-plan.ts`), and its two selection-key
  parameters are non-optional TypeScript arguments — no code path can
  insert a `path_plan` row with either column null. Flagging as a possible
  future hardening step (see Next) rather than adding it now — out of
  #71's scope.
- **Lost-race handling returns the winner's row id rather than swallowing
  the error the way `completeDiscovery` does for `identity_report`.**
  Checked the actual contracts first: `POST /api/generate-path-options`
  must return a valid `artifact_id` for the frontend (`app/path/page.tsx`)
  to start polling, and `generatePathPlan`'s sole caller
  (`app/api/select-path/route.ts`) treats a `null` return as a genuine
  failure and surfaces a hard 500. Simply swallowing the race (like
  `completeDiscovery` does, returning `false`/`null` unconditionally) would
  turn a harmless lost race into a hard user-facing error for the losing
  concurrent request, even though the winning request's generation is
  running fine. Re-resolving and handing back the winner's id keeps both
  requests functionally successful.
- **The lost-race fallback lookup uses no status filter**, closing even the
  theoretical (not realistic) edge case where the winner's row resolves to
  `ready`/`failed` before the fallback lookup runs — free to do since
  `getCurrentArtifact` already orders by `created_at desc`, so the winner's
  row is the newest regardless of its status by that point. Confirmed
  `runGeneration`/`runPlanGeneration` both fire via `after()`, which only
  starts after the HTTP response is sent — so in practice the winner's row
  can't plausibly resolve past `generating` before the loser's fallback
  lookup runs anyway; this is a zero-cost hardening, not a fix for an
  observed failure.
- **Did not grant test-user entitlements in the verification script.**
  Confirmed `NEXT_PUBLIC_OPEN_ACCESS=true` in `.env.local` (the value the
  currently-running dev server was started with) bypasses entitlement
  checks entirely, both server-side (`lib/entitlements.ts`'s
  `hasEntitlement`) and client-side (`app/path/page.tsx`,
  `app/plan/page.tsx`'s own `NEXT_PUBLIC_OPEN_ACCESS !== 'true'` guards) —
  confirmed via grep that `scripts/verification/session.mts` grants no
  entitlements itself. Adding an explicit `grantEntitlement()` call would
  have been redundant for this pass.
