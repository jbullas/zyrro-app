### The `.card h3` / `.named-identity` collision — two-step fix
- **Caught, not assumed.** The brief explicitly warned: `IdentityCard.tsx`
  on `/dashboard` renders `<h3 className="named-identity">` inside its own
  `.card` div. Checked before implementing (not after) — confirmed
  `.named-identity`'s only rule was `{ text-transform: uppercase; }`, no
  font-size/weight override, so the new `.card h3` rule would cascade onto
  it and shrink it from `18px`/`600` to `15px`/`700` as an unintended
  side effect on a page outside this brief's own described scope.
- **Decided correctly the first time this was presented: add a targeted
  override.** The fix was not implemented at that point in the session —
  an execution gap, not a decision reversal. It surfaced later, when a
  review of the verification script's `/dashboard` check found it was
  written as a passive `console.log` of the computed font-size/weight
  rather than a hard assertion, which is what revealed the override
  didn't actually exist yet in `globals.css`.
- **Fixing it then surfaced a real specificity bug.** A plain
  `.named-identity { font-size: 18px; font-weight: 600; }` rule has
  specificity `(0,1,0)`, which loses to `.card h3`'s `(0,1,1)` regardless
  of source order — the override as first written would have been
  silently ineffective. Caught via specificity math before it shipped,
  not discovered via a failing test. Fixed with
  `.identity-card-header .named-identity { font-size: 18px; font-weight:
  600; }` — specificity `(0,2,0)`, unconditionally wins. Verified live via
  computed style on `/dashboard`: `18px`/`600`, confirmed restored.

### Stale Turbopack `.next/dev` cache — recurred, same root cause and fix
- The exact same failure mode from the 2026-08-05 (→ actually 2026-08-06,
  see the dating note below) full-restructure session recurred mid-way

  invalidate on every source edit in this environment; `rm -rf .next` +
  fresh `npm run dev`, reconfirmed via a direct `curl` of the served CSS
  chunk before re-running verification. Recognized and fixed faster this
  time since the signature (served CSS matching a *prior* edit, not the
  latest one) was already known from last session's note. **This is now a
  second confirmed occurrence, not a one-off** — worth treating as a
  standing risk for this dev environment, not a fluke: after any
  `app/globals.css` edit made while a dev server is already running,
  re-verify the served CSS chunk directly via `curl` before trusting a
  live check, and if it's stale, don't bother debugging HMR further, just
  wipe `.next` and restart.

## 2026-08-06 — #100: spacing fixes (cover divider, card rhythm, docs, footer width)

Per `docs/briefs/100-spacing-fixes-brief.md`, four small independent CSS
fixes surfaced by reviewing the live restructured report (Ingrid sample)
following the card-consistency pass above. `app/globals.css` only, no
JSX/component changes. Fix 2 touches `.constellation-card-body`,
`.core-statement`, `.tension-block`, and `.scoring-chips` — all shared by
`/identity`, `/path`, and `/plan` via `ConstellationCard` — so verification
covered all three pages, not just `/identity`, same as the last brief.

### Changed
- **Fix 1 — no divider between Cover and Domain Profile.**
  `.report-sections` gets its own `border-top: 0.5px solid
  rgba(0,0,0,0.07)` and `padding-top` raised from `8px` to `28px`,
  matching the divider-to-content gap `.report-section + .report-section`
  already uses everywhere else. Root cause: the adjacent-sibling selector
  only fires between two `.report-section`s — Domain Profile is
  `.report-sections`' first child, preceded by the separate
  `.report-cover` div, so it never matched and had no divider above it
  while every later section did.
- **Fix 2 — core-statement/tension-block vertical rhythm.** New
  `.constellation-card-body > * + * { margin-top: 16px; }` — the
  container now owns vertical spacing between its children uniformly,
  instead of each special block managing its own gap to neighbors (same
  "container owns spacing" principle as the card-consistency pass).
  `.core-statement` and `.tension-block` keep their own padding/border/
  background (what makes them visually special) but stop declaring
  `margin-top` themselves. `.scoring-chips`' `margin-top: 14px` dropped
  the same way — its own `border-top` still provides a visual divider on
  top of the container's spacing. Also removed the now-fully-dead
  `.constellation-card .evidence-analysis:last-child { padding-bottom:
  14px; }` rule (`.evidence-analysis` never lands as the last child in
  the current markup on any of the three pages, confirmed before
  removing, not assumed).
- **Fix 3 — documentation paragraph spacing.** New `.documentation p + p
  { margin-top: 12px; }`. Root cause: `.documentation p` set no margin of
  its own and the global `p` rule is `margin: 0`, so the four Research
  Foundation pillar paragraphs stacked with zero gap between them. Only
  fires between consecutive paragraphs, not before the first paragraph
  after a heading — `.documentation h2`/`h3`'s own margin already
  handles that gap, untouched.
- **Fix 4 — `.report-footer` width.** Picks up the same `18px`
  horizontal inset `.report-sections` already had (`padding: 24px 18px
  0`, was `padding-top: 24px` only). Root cause: `.report-footer` is a
  sibling of `.report-sections`, not nested inside it, and their shared
  parent (`.report-scroll`) carries no horizontal padding of its own —
  `.report-footer` never got an equivalent inset, so it rendered
  edge-to-edge wider than every other section.

### Two cascade-collision bugs, found via pixel measurement, not in the brief's literal text
- This verification pass measured actual `getBoundingClientRect()`
  vertical pixel offsets, not just horizontal ones — the previous brief's
  verification measured horizontal offsets only, which is exactly how
  fix 2's regression got through undetected in the first place. That
  precision caught two real bugs the brief's own literal CSS didn't
  anticipate, both confirmed with Miroslav before fixing rather than
  silently patched or silently shipped broken:
  - **`.tension-block` and `.scoring-chips`** (both named in the brief's
    own fix 2) still declared their own `margin-top` — `.tension-block`
    via a `margin: 0 16px` shorthand, `.scoring-chips` via an explicit
    `margin-top: 0`. Both are single-class selectors at the exact same
    specificity, `(0,1,0)`, as the new `.constellation-card-body > * +
    *` rule, and both are declared *later* in the file — so at equal
    specificity, source order wins and their own `margin-top: 0` silently
    canceled the container's intended `16px`. Measured `0px` where the
    brief's own Verification section explicitly expected `16px`.
    **Fix pattern:** drop the colliding `margin-top` declaration and let
    the container rule own it. `.tension-block` switched from the
    `margin: 0 16px` shorthand (which can't partially omit one side) to
    `margin-left: 16px; margin-right: 16px;` declared separately, so no
    `margin-top` is set by this rule at all. `.scoring-chips`' explicit
    `margin-top: 0` line removed outright.
  - **`.evidence-analysis`** — same root cause, not in the brief's fix 2
    CSS list at all (the brief's own text only says "same issue on
    /path/plan, since neither page's `ConstellationCard` usage was
    touched," without accounting for `.evidence-analysis`'s own `margin:
    0` colliding the identical way). Didn't surface on `/identity`
    (collapsed to a bare `<p>` in the prior brief, no competing rule) or
    on `/path` (always the first card child there, so `* + *` never
    targets it, same reason `.core-statement` was never affected). Did
    surface on `/plan`, where `.evidence-analysis` renders `phase.body`
    as the *second* card child, after `.core-statement` — measured `0px`
    gap instead of `16px`. **Fix pattern, adapted:** removed the
    `margin: 0;` line entirely rather than adding `margin-left`/`
    margin-right` like `.tension-block` — `.evidence-analysis` already
    gets its horizontal inset from its own `padding: 14px 16px 0`, so
    adding margin too would have doubled it. Falls back to the initial
    `0` when it is the first child (no regression on `/path`), and lets
    the container's `16px` apply cleanly when it isn't (fixes `/plan`).
