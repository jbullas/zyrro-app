## 2026-08-08 — #106/#105: discovery answers storage fix + 5000-char cap

Per `docs/briefs/106-105-discovery-answers-storage-fix-brief.md`. Fixes a
live 494 `REQUEST_HEADER_TOO_LARGE` on `/auth/callback`: raw discovery
answers were being passed into `signUp()`'s `user_metadata`, which Supabase
embeds directly in the session JWT/auth cookie, blowing past Vercel's
request header size limit once answers grew large enough. Live-reproduced
at session start.

### Changed
- **New migration `supabase/migrations/20260808000000_pending_discovery_answers.sql`**
  — `pending_discovery_answers` table (`id` uuid PK default `gen_random_uuid()`,
  `answers` jsonb, `created_at`). No RLS — service-role-only access, no
  authenticated user exists yet at insert time. Applied live via the
  Supabase SQL Editor and confirmed with a round-trip insert/read/delete.
- **New route `app/api/stage-discovery-answers/route.ts`** — accepts the 13
  `{ question_number, answer_text }` pairs pre-signup (no auth check by
  design), validates shape (count, `question_number` range, `answer_text`
  is a string), inserts one row via service-role client, returns `{ id }`.
- **`app/start/page.tsx`** — `handleContactSubmit` now stages answers via
  `POST /api/stage-discovery-answers` before calling `signUp()`, and passes
  only `{ display_name, discovery_token: id }` as metadata — no
  `discovery_answers` key at all. Staging failure surfaces through the
  existing `contactError` pattern and skips `signUp()`. #105: the 1000-char
  cap is raised to 5000 in all four spots (`updateAnswer`, `handleFinishState3`'s
  payload mapping, the contact-submit parsed-answer mapping, and the
  character counter UI), with the counter's warning threshold scaled
  proportionally from 900 to 4500.
- **`lib/kickoff-identity-generation.ts`** — reads
  `user.user_metadata?.discovery_token` instead of `discovery_answers`.
  When present, resolves it against `pending_discovery_answers` via the
  service-role client and deletes the row after a successful read (raw
  free-text shouldn't sit indefinitely in an unowned table). If the token
  doesn't resolve, or is absent entirely, falls through to the existing
  `rawAnswers.length === 0` branch unchanged — same State-3 fallback as
  before.

### Verification
- `npx tsc --noEmit` and `eslint` both clean on all changed/new files.
- **Live**, via two ad hoc scripts in `scripts/` (deleted after, not
  committed), since a real end-to-end run hit Supabase's built-in
  email-rate-limit partway through the session:
  - **Part A** — drove the real `/start` UI through 13 answers (one at
    4800 chars) and the real `POST /api/stage-discovery-answers` call,
    then intercepted the outgoing `supabase.auth.signUp()` network request.
    Confirmed payload is exactly `{ display_name, discovery_token }` (322
    bytes) with no `discovery_answers` key — vs. ~62KB+ if the 13 raw
    4800-char answers had still been embedded. Char counter UI confirmed
    reading `4800/5000`.
  - **Part B** — using `scripts/run-verification.mts`'s existing bootstrap
    helper (admin-generated links don't hit the email rate limit), seeded
    a real `pending_discovery_answers` row and drove the real
    `/auth/callback` route with a user whose metadata carried its token.
    Confirmed the row resolves correctly, is deleted exactly once,
    `identity_report` generation kicks off (`status: 'generating'`), and
    the profile is created with the right name.
  - Final check confirmed zero stray `pending_discovery_answers` rows and
    zero orphaned test users left behind.

### Decisions
- Staged answers server-side under an opaque token rather than any
  alternative (e.g. shrinking/compressing metadata) — decouples answer
  size from cookie size entirely, and as a side effect removes the only
  reason the 1000-char cap existed, so #105 folded into the same brief.
  Decided 2026-08-08.
- No cleanup job for orphaned `pending_discovery_answers` rows (staged but
  never confirmed) — low priority, no PII risk beyond free-text answers,
  explicitly deferred to its own future ticket.
