### Changed

`supabase/migrations/20260826000000_path_checkpoint_session_stage_a.sql`
(committed and run against the live dev Supabase project):
- Extended `artifacts_type_check` with two new types.
- `path_checkpoint_session` — **mutated in place** (one row per user),
  not append-only, per the brief's explicit instruction not to apply
  the Tier C pattern here. New `current_stage` column (own column,
  same precedent as `path_plan`'s `path_options_artifact_id`/`path_id`)
  plus the existing `content` jsonb column holding
  `{ stage_outputs: { stage1: {...}, stage2: {...}, ... } }`, each key
  overwritten independently on redo.
- `path_checkpoint_result` — a normal Tier C append-only artifact
  (same `getCurrentArtifact` read pattern and generating-guard shape as
  `identity_report`/`identity_reframe`), written once at session
  completion. New `path_checkpoint_session_id` column links it back to
  the session that produced it (self-referential FK, same pattern as
  `path_plan`'s `path_options_artifact_id`).
- Two new partial unique indexes
  (`artifacts_one_path_checkpoint_session_generating_per_user`,
  `artifacts_one_path_checkpoint_result_generating_per_user`), same
  shape as #59/#71/#98.
- New, separate table `path_checkpoint_exchanges` (checkpoint log —
  what was presented, what the user chose/typed) — reuses the
  `conversations`/`messages` turn-taking *shape* (`role` + `content` +
  `created_at` ordering) but is its own table. RLS: insert/select for
  the owning user only, no update/delete policy (append-only by
  omission; service role still bypasses RLS as usual).

`lib/path-checkpoint.ts` (new) — the state-machine module owning every
mutation to a `path_checkpoint_session` row: `startCheckpointSession`
(insert-then-catch-23505-then-reread, #71's create-race pattern),

see Decisions below), `recordStageOutput` (stage-scoped overwrite),
`advanceToStage`, `logExchange`, `completeCheckpointSession` (writes
the Tier C `path_checkpoint_result` row, links it back, marks the
session `complete`).

`lib/artifacts.ts` — `ArtifactType`/`ArtifactStatus` unions extended
with the two new types and `awaiting_checkpoint`/`complete` (type-only

`scripts/verify-129-stage-a.mts` (new, kept per Miroslav's call at

All 5 scenarios passed on a single run
(`npx tsx --env-file=.env.local scripts/verify-129-stage-a.mts`):

1. **Walk through several stages** — session created (stage 1,
   `generating`) → stage 1/2 placeholder outputs recorded → status
   correctly `awaiting_checkpoint` after stage 2.
2. **Checkpoint exchange (presented → redo → proceed)** — a "presented"
   entry logged, then a redo (stage 2 overwritten to a v2 placeholder),
   then a proceed (advanced to stage 3). Repeated once more at stage 4.
   Confirmed via **fresh, independent DB reads** (not reused in-memory
   objects) that stage 2's and stage 3's outputs were byte-identical
   (`JSON.stringify` equality) before and after each sibling stage's
   redo. The full 8-entry exchange log was read back independently by
   `session_id` (not through the session row) and matched the exact
   expected role sequence
   (`presented, redo, proceed, presented, redo, proceed, presented, proceed`).
3. **Abandoned session** — created, advanced to stage 2, then
   deliberately not touched again ("closed tab" simulation); a fully
   separate later read via `getCurrentArtifact` confirmed
   `current_stage`/`status` intact.
4. **Concurrent generation attempts**, tested as two distinct races
   (see Decisions — the brief's guard only covers one of them):
   - **4a, creation race**: two concurrent `startCheckpointSession`
     calls for the same fresh user resolved to the identical row id
     (loser caught `23505`, reread and reused the winner's row); a
     direct count confirmed exactly one `path_checkpoint_session` row
     exists for that user.
   - **4b, mid-flow claim race**: two concurrent `claimGeneration` calls
     against the *same existing* row — exactly one returned the row,
     the other `null` (the loser-reuses-winner contract, enforced by a
     conditional `UPDATE ... WHERE status != 'generating'` rather than
     the partial index, since two `UPDATE`s on one row can't violate a
     uniqueness constraint against each other).
5. **Completion** — `completeCheckpointSession` wrote a placeholder
   `path_checkpoint_result` row; `getCurrentArtifact` resolved the same
   row; `path_checkpoint_session_id` correctly linked back; the session
   row read back as `status: 'complete'`.

### Decisions

- **Renamed `path_selection_session`/`path_selection_result`/
  `path_selection_exchanges` (the brief's literally proposed names) to
  `path_checkpoint_*`** before writing anything live — flagged to
  Miroslav that the brief's proposed name collides badly with the
  pre-existing, unrelated `public.path_selections` table (#10, project
  naming / "which path did the user pick" event log). Confirmed with
  him before implementing; `path_selections` itself is completely
  untouched by this migration.
- **Two separate concurrency guards, not one**, after finding the
  brief's literal instruction ("same partial-unique-index-on-generating
  pattern as #59/#71") only actually protects the initial *creation*
  race — #59/#71's precedent is append-only (a race between two
  INSERTs), but this type is mutated in place, so a *second* race (two
  concurrent claims on the one already-existing row — e.g. a
  double-click on "proceed" once a session already exists) can't be
  caught by any unique index at all, since two UPDATEs on the same row
  never violate a uniqueness constraint against each other. Implemented
  the brief's literal index for the creation race, and added a
  conditional-UPDATE `claimGeneration` helper for the mid-flow race —
  both are exercised as separate scenarios (4a/4b) in the verification
  script. Flagged in the migration file's own comments, not silently
  decided.
- Kept `scripts/verify-129-stage-a.mts` (Miroslav's call at review) —
  Stage B builds real reasoning directly on top of this state machine,
  so rerunning it is a cheap regression check going forward.
- Final artifact (`path_checkpoint_result`) writes `status: 'ready'`
  directly rather than `generating` → `ready`, since Stage A has no
  async generation step to model yet (placeholder content is
  synchronous). Stage C will need to add the real
  `generating`-then-update-to-`ready` transition once actual LLM
  content generation lands, matching `path_options`'s existing shape.
- Discovered in passing, not part of this ticket: a live-only Postgres
  trigger auto-creates a `profiles` row on `auth.users` insert — it's
  not in any tracked migration (`profiles_baseline.sql` shows no such
  trigger). The verification script's test-user bootstrap had to switch
  from `insert` to `upsert` on `profiles` after hitting a duplicate-key
  error from this. Worth tracking down and adding a migration for at
  some point, but out of scope here — noting it so it isn't rediscovered
  from scratch next time.
