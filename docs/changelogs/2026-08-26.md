### Decisions

- **Renamed `path_selection_session`/`path_selection_result`/
  `path_selection_exchanges` (the brief's literally proposed names) to
  `path_checkpoint_*`** before writing anything live — flagged to
  Miroslav that the brief's proposed name collides badly with the
  pre-existing, unrelated `public.path_selections` table (#10, project
  naming / "which path did the user pick" event log). Confirmed with
  him before implementing; `path_selections` itself is completely
  untouched by this migration.
- **Two separate concurrency guards, not one**, after finding the
  brief's literal instruction ("same partial-unique-index-on-generating
  pattern as #59/#71") only actually protects the initial *creation*
  race — #59/#71's precedent is append-only (a race between two
  INSERTs), but this type is mutated in place, so a *second* race (two
  concurrent claims on the one already-existing row — e.g. a
  double-click on "proceed" once a session already exists) can't be
  caught by any unique index at all, since two UPDATEs on the same row
  never violate a uniqueness constraint against each other. Implemented
  the brief's literal index for the creation race, and added a
  conditional-UPDATE `claimGeneration` helper for the mid-flow race —
  both are exercised as separate scenarios (4a/4b) in the verification
  script. Flagged in the migration file's own comments, not silently
  decided.
- Kept `scripts/verify-129-stage-a.mts` (Miroslav's call at review) —
  Stage B builds real reasoning directly on top of this state machine,
  so rerunning it is a cheap regression check going forward.
- Final artifact (`path_checkpoint_result`) writes `status: 'ready'`
  directly rather than `generating` → `ready`, since Stage A has no
  async generation step to model yet (placeholder content is
  synchronous). Stage C will need to add the real
  `generating`-then-update-to-`ready` transition once actual LLM
  content generation lands, matching `path_options`'s existing shape.
- Discovered in passing, not part of this ticket: a live-only Postgres
  trigger auto-creates a `profiles` row on `auth.users` insert — it's
  not in any tracked migration (`profiles_baseline.sql` shows no such
  trigger). The verification script's test-user bootstrap had to switch
  from `insert` to `upsert` on `profiles` after hitting a duplicate-key
  error from this. Worth tracking down and adding a migration for at
  some point, but out of scope here — noting it so it isn't rediscovered
  from scratch next time.

**Caught in review, fixed before anything ran**: two real bugs in the first
draft of `path-checkpoint-response/route.ts`, both flagged directly rather
than smoothed over —
1. `recordChosenCandidate`'s first draft never actually wrote the chosen
   candidate id into `content` (`content: supabase.rpc ? undefined :
   undefined`, leftover placeholder junk) — fixed to merge into
   `priorContent`, same pattern `recordStageOutput` already uses.
2. An `as never` cast on a Stage 4 redo call was hiding a real type
   mismatch (the surviving-overlaps shape passed didn't actually match what
   Stage 4 expected) — fixed by narrowing `runStage4Candidates`'s parameter
   type to `Pick<Stage3Output, 'surviving'>` (all it ever reads) instead of
   requiring a full `Stage3Output`, removing the need for any cast.

**A second, broader concurrency gap found on audit** (explicitly requested,
not assumed clean): the redo path claimed generation via `claimGeneration`
before proceeding, but the `proceed` path didn't — two concurrent `proceed`
clicks could both call `advanceToStage` and both fire background work.
Worse, *any* synchronous throw after a successful claim (not just the one
stage-4-invalid-choice branch already patched) would strand a session at a
false `'generating'` status forever, since nothing else would ever reset
it. Restructured rather than spot-patched: every path now claims once,
upfront, and everything after that claim runs inside one `try/catch` in
`POST()` that resets status back to `awaiting_checkpoint` on any exit that
isn't a background handoff or an explicit status-settle.

### A significant discovery, unrelated to Stage B, found incidentally

Driving personas through `/auth/callback` (required to get authenticated
test sessions — no route in this project supports password login) is
supposed to be a no-op for a user who already has a `ready` `identity_report`
(`completeDiscovery`'s idempotency guard). It wasn't: real, unwanted
Layer 1 + Layer 2 regenerations fired for **all 3 personas**, and one hit a
real OpenAI rate limit and failed outright.

**Root cause, confirmed by direct reproduction against real data**:
`completeDiscovery`'s existence check used `.maybeSingle()` with no
`.order()`/`.limit(1)` — `identity_report` is append-only (#59), so any
user who has ever regenerated more than once (the normal state, not an
edge case) has multiple `ready` rows, and `.maybeSingle()` throws
`"multiple (or no) rows returned"` in that case. The thrown error was also
silently swallowed (only `data` was destructured), so the guard fell
through as if no report existed at all — for *every* real user with 2+
`ready` rows, on *every* subsequent login. Reproduced directly against
Leona's real data (8 accumulated `ready` rows): confirmed `PGRST116` before
the fix, a real row with no error after.

**Fixed in its own commit** (`lib/complete-discovery.ts`, unrelated file to
everything else in this brief): added `.order('created_at', {ascending:
false}).limit(1)` before `.maybeSingle()`, same narrowing
`lib/artifacts.ts`'s `getCurrentArtifact` already uses for exactly this
reason — and, since the commit's own message named the silent
error-swallow as part of the bug, also captured and checked that error
(`existingCheckError`), logging it and bailing out (`return false`) rather
than falling through, matching this same function's existing
`insertError`-handling precedent. Verified via direct query reproduction
against Leona's real 8-row data both before and after. One inert `failed`
row this incident left on Katalin's account was cleaned up (harmless per
this table's established "failed rows are noise, not history" convention).
