## 2026-09-15 — #146 (reopened): Options bootstrap 500 — investigated, fixed, live-verified

### Changed

- **Investigation** (`docs/briefs/146-investigate-options-bootstrap-error.md`): traced the
  "Something went wrong." screen appearing right after Direction's 3rd screen completes (first-ever
  Options bootstrap) to the same idle-pooled-connection transient-failure class as #141, at a call
  site #141's fix never reached: the raw `.insert(...).select(...).single()` inside
  `startOrReuseOptionsSession` (`lib/path-options-session.ts`). It only fires once per user (their
  first Options bootstrap) and wasn't wrapped in `withDbRetry`, unlike `getCurrentArtifact`/
  `hasEntitlement` (#141's shared primitives) — an error there threw uncaught, with no try/catch
  anywhere in `GET /api/path-options`, so Next.js returned a bare 500 with no JSON body, collapsed
  client-side into the generic bootstrap error message. No Vercel log access in this environment, so
  the real incident's exact status/body couldn't be recovered from history — reported as code-audit
  confidence, not a captured live incident, same honest-stop posture #141's own first pass used.
- **Fix** (`docs/briefs/146-fix-options-session-retry.md`): wrapped all three unretried raw Supabase
  calls in `lib/path-options-session.ts` in `withDbRetry` — the `startOrReuseOptionsSession` insert
  (the confirmed root cause), plus `claimGeneration` and `appendCandidates` (same vulnerability
  class, flagged by the investigation as present but not implicated in this specific repro; fixed in
  the same pass rather than left as a known gap, per the brief's explicit in-scope call). Added a
  try/catch around `GET /api/path-options`'s body in `app/api/path-options/route.ts` so any future
  uncaught failure returns a controlled `{ error: 'Something went wrong.' }` / 500 JSON response
  instead of degrading to the same undiagnosable bare-500 shape #146 just went through. Existing
  handled error paths (401/403/404/409) are unchanged — the catch-all only covers what previously
  fell through uncaught.

### Decisions

- Fixed all three unretried call sites in `lib/path-options-session.ts` in one pass rather than only
  the confirmed root cause — the brief made this call explicitly (identical pattern, identical fix
  cost, avoids leaving a known gap for a future incident), not a scope expansion made mid-session.
- Did not attempt to force a live repro of the actual idle-reconnect stall — non-deterministic, no
  on-demand trigger, same explicit precedent #141 set. The brief's optional forced-`fetch`-intercept
  nice-to-have wasn't pursued either: `withDbRetry` itself is unchanged, already-tested code (#141's
  own forced-failure test already covers its retry/recovery semantics), so a fresh mock test of the
  same function wrapping new call sites wouldn't have added real signal.

### Live-verification results

- Project-wide `tsc --noEmit`: clean, no output.
- `next build`: clean, all routes compiled, no errors.
- Real browser pass (fresh synthetic user via `scripts/run-verification.mts`, seeded `identity_report`
  + a complete `path_direction_session` + an active `entitlements` row directly, then loaded `/path`
  fresh — the exact first-ever-Options-bootstrap moment #146's fix targets). Took a few iterations to
  get a clean pass: the first two attempts never fired any `/api/path-options` request at all, traced
  to `NEXT_PUBLIC_OPEN_ACCESS` being `false` in this `.env.local` (not `true`, as CC's local memory
  entry `reference_local_test_auth_bootstrap` claims — that memory is stale) — without a real
  `entitlements` row, `app/path/page.tsx` sends the test user down the `unpaid` branch instead of
  `checkpoint-flow`, so Direction/Options never load. After seeding an active entitlement directly,
  `GET /api/path-options` returned **200** and zero `[db-retry]` log lines appeared in the dev server
  output (`grep -c '[db-retry]' /tmp/dev-server-146.log` → `0`), confirming the happy path takes zero
  retries and the fix doesn't add latency.
- One run after that showed a *different* pre-existing message on the page ("We couldn't generate
  your options...", from `OptionsFlow.tsx`) even though the bootstrap GET itself had already returned
  200. Confirmed via the dev server log this was unrelated to #146: `Path options initial generation
  failed: Error: 401 Incorrect API key provided`, with a stack trace through `runInitialGeneration` →
  `generateCandidateBatch` → `requestOptionDrafts` → `getChatCompletion` (`lib/llm.ts:14`) — the real
  OpenAI call the background candidate-generation job makes *after* the bootstrap request already
  succeeded. This is a stale/invalid OpenAI key in the local `.env.local`, a separate failure surface
  from the bootstrap request this ticket fixes, not a regression from this fix.
- Final run asserted directly on the ticket's actual scope (GET `/api/path-options` status + absence
  of the specific #146 bootstrap error message, not the unrelated generation-failure message) and
  passed: `GET /api/path-options` → 200, zero client console errors, no #146 bootstrap error screen.
- Throwaway verification script (`scripts/_tmp/verify-146.mts`) deleted after the run, same
  write-it/run-it/delete-it posture as prior sessions' ad hoc checks — not part of the repo.
