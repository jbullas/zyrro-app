### Incident: `node_modules` wiped by `git worktree remove --force`

- While verifying commit `61e207a` actually compiled clean (not just the
  working tree), I created an isolated `git worktree add --detach` checkout
  and, to reuse the existing install rather than duplicate it, linked its
  `node_modules` to the real one via a Windows NTFS junction. `git worktree
  remove --force` afterward appears to have treated that junction as an
  ordinary subdirectory rather than a link to unlink as a unit — junctions
  are transparent at the filesystem level, so its recursive delete walked
  through it and deleted all ~555 real packages from the actual repo's
  `node_modules`, then removed the now-empty junction/directory as normal.
  `.git/worktrees/` metadata came out looking perfectly clean, since git
  has no way to know it deleted through a reparse point.
- Confirmed via timestamps and a before/after count (372 real entries
  immediately before the `git worktree remove --force` call, per an
  explicit check right after a preceding `rmdir` on the junction failed
  safely and confirmed both the junction and the real directory still
  intact; zero entries immediately after) that this command, not the
  earlier `rmdir`, was the actual cause — the `rmdir` was the one flagged
  as risky going in, but it was the one that behaved safely (Windows
  refused to treat the junction as a plain empty directory); the danger
  was one command later than either of us expected.
- No source files, commits, or `.git` history were touched — scoped
  entirely to `node_modules`, which is derived/reinstallable and not
  tracked in git. Recovered with `npm install` (459 packages restored,
  `next@16.2.1` matching `package.json`'s pin exactly). Re-ran `npx tsc
  --noEmit` and `npx eslint app/path/page.tsx` against the real repo state
  afterward to confirm the recovery didn't mask or introduce anything —
  both clean, identical to the pre-incident results.

### Live-verification results — 5/5 pass

`scripts/verify-134-slice1.mts`, driven against a real (synthetic,
bootstrapped-then-torn-down) test user via `scripts/run-verification.mts`:

1. Must-haves: select 3 energisers, 4th option disables, deselect one, 4th
   re-enables, submit. **PASS**
2. Must-avoids: same disable/re-enable check against `friction_points`,
   submit. **PASS**
3. Ideal-life: free text, submit. **PASS**
4. Complete summary shows the saved must-haves/must-avoids/ideal-life back
   correctly — checked via DOM text and a direct read of the persisted
   `path_direction_session` row. **PASS**
5. Refreshing the browser mid-flow (after must-haves, before must-avoids)
   resumes on the must-avoids step from real server-side state, not a
   restart — confirmed the DB itself had `must_haves` persisted and
   `must_avoids` still `null` at the moment of reload, so this isn't a
   client-side fluke. **PASS**

First run of the script logged 9 failures, but that was a bug in the test
script itself, not the app: the wait condition `text=CHECKPOINT 1` matches
every screen in the flow (it's the eyebrow label on all four), so it
resolved instantly against the still-on-screen ideal-life step rather than
waiting for the submission's request to actually land, and the DOM/DB
assertions ran mid-flight. Fixed the wait to target text unique to the
complete screen; re-run passed clean (all 22 assertions).
