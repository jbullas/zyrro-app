# #144 — "Your Path" report: live-review fixes (post-#139)

Real feedback from the first live generation after #139 shipped. This is follow-up
work, not a #139 reopen — #139 is Done and stays Done. Touches render
(`PathReportFlow.tsx`), prompt (`lib/prompts/path-report.ts`), schema
(`lib/generate-path-report.ts`), route (`app/api/path-report/route.ts`), and CSS
(`app/globals.css`).

## Global rule — apply everywhere in this file's scope

**No em dashes, anywhere.** Not in static help text (every `_EXPLANATION` constant in
`PathReportFlow.tsx` currently uses them — audit and rewrite all of them, not just the
one flagged below), and not in LLM-generated prose either — add an explicit
instruction to `PATH_REPORT_PROMPT` banning em dashes in its own output. This is a
blanket style rule, not scoped to one section.

## Cover

- Add a `cover-context-line`, same pattern as `/identity`
  (`{cover.prepared_for} · {cover.identity_context}`). Both fields already exist on
  `identityReport.cover`, already loaded in `app/api/path-report/route.ts` — thread
  them into `PathReportContent` (new fields, e.g. `prepared_for`/`identity_context`,
  attached by the route the same way `chosen_candidate`/`comments` are today, not
  generated by the prompt).
- Remove the `identity-thesis` class from the Summary paragraph. That class is a
  large, punchy one-liner treatment — correct for the `core_statement` thesis line,
  wrong for a full paragraph (this is also almost certainly why Summary reads as "a
  tad too long": the styling itself makes any paragraph feel long). Summary needs its
  own plain-body paragraph style, not reused from `identity-thesis`.
- Summary: trim slightly. No structural change, just tighten the word target a little
  in the prompt.

## What This Could Be

- New help text — rewrite. Not because the current one is factually wrong, but
  because "uninspiring" and structurally wrong: this section's whole job is to paint
  one vivid, confident vision, not to hedge. The help text should set that expectation
  directly rather than just explaining scope.
- **Content fix, and this is the real one:** the actual generated content currently
  reads as a stacked list of branches ("this could become X, or expand into Y, scope
  could vary from A to B") — hedging dressed up as flexibility. Rewrite the prompt
  instruction so genuine open-endedness (scale, form — things the user hasn't told us)
  lives in *what the vision deliberately doesn't specify*, not in a visible list of
  alternatives presented side by side. One confident, inspiring, singular vision
  statement that simply doesn't pin down the parts that are genuinely undecided —
  not a menu.

## Why It Fits

- New help text — rewrite (no em dashes, per global rule).
- **Render change:** split into two real cards, each with its own `<h3>` heading
  (something like "What You Can Do" / "What You Want," final wording up to whoever
  writes the copy) instead of one card containing two `<p>`s. Schema-wise `why_it_fits`
  can stay a single string split on the existing `\n\n` separator (as today) — this is
  a render change, not necessarily a schema change, unless splitting into two labeled
  cards reads better as two separate generated fields. Your call on which is cleaner
  to implement; either is acceptable as long as the visual result is two distinct
  headed cards.
- **Content fix:** tighten the must_haves/must_avoids grounding instruction. The ask
  isn't to literally name/quote a must_have or must_avoid — it's to weave in enough
  concrete specificity tied to what the user actually said that they recognize their
  own input reflected in the copy, even if they don't remember their exact original
  wording. The current instruction ("grounded in must_haves... where relevant") is too
  loose to guarantee that recognizability.

## Where This Leads

- New help text — rewrite (no em dashes).
- Rename section label to "Day in Life" (or close variant — final wording your call).
  This is a label/eyebrow change only, no change to `life_it_leads_toward`'s content
  rules — the content itself was confirmed good.

## How You Get There — the weakest section, most of the real work is here

- New help text — rewrite (no em dashes).
- **`decision` field must be phrased as an imperative decision statement**, not a bare
  noun phrase — e.g. "Determine which product categories to focus on first," not
  "Which product categories to focus on." Update the prompt's own instruction and
  example for this field accordingly.
- **Remove the `evidence-analysis` CSS class from this section's paragraphs** in
  `PathReportFlow.tsx`. That class was inherited from the old `master_strategy` render
  and was never re-evaluated for whether it's the right styling for this new content
  — it likely isn't (it's probably a muted/small citation-style treatment, wrong for
  primary body content here).
- **Deepen `why_it_matters` substantially.** Currently 30-70 words and shallow. Needs
  real elaboration covering: what the decision is actually about, why it matters
  concretely, why it matters *at this stage* of this specific path (not a claim about
  ordering relative to other decisions — each decision explains its own timing
  independently, this does not reintroduce cross-decision sequencing), and what
  resolving it enables next. Expand the word range accordingly (your call on the exact
  new range, but meaningfully longer than 30-70 words).
- **`live_options` needs a real schema change** — currently `string[]` (bare short
  labels, rendered as flat chips). Change to an array of objects, each option carrying
  a short label plus real context — e.g.:
  ```ts
  live_options: { option: string; context: string }[]
  ```
  Render change to match: each option becomes its own labeled sub-section (heading or
  bold label + a sentence or two of context), not a `ChipRow` of bare pills. "Only
  pills are pretty but useless" — the fix is giving each option enough of its own
  space to actually explain the direction, not just name it.

## CTA

- **Reuse the existing `.section.cta`/`.card.cta` styling system verbatim — do not
  invent new styling.** `components/ReframeCtaBlock.tsx` is the existing, working
  reference (used on `/identity`): `<div className="section cta">` wrapping a centered
  eyebrow + `<h2>`, then `<div className="card cta">` containing the actual pitch
  content and a `PrimaryButton`. `PathReportFlow.tsx`'s current CTA block is a plain
  `.card` with inline `textAlign: center` — replace that markup with the real
  `.section.cta`/`.card.cta` pattern. This is a render-only fix; the naming
  dialog/Mentor-pitch content itself doesn't need to change, just the wrapper styling.
