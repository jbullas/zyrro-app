# Brief: #103 — Domain Profile LLM-generated summary text

## Goal
`domain_profile` currently holds only five numeric scores. Add a new field,
`domain_profile_summary`, generated by Layer 2 alongside the rest of the
report: ~80–110 words of prose summarizing which domains this person's
strongest patterns cluster in, and what that concentration or spread means
operationally.

## Why a sibling field, not nested in `domain_profile`
`lib/generate-identity-report.ts` already overwrites the report's
`domain_profile` object post-generation with `computeDomainProfile(analysis.signatures)`
— a deterministic recomputation from the Detection Engine's real signature
scores, replacing whatever Layer 2 produced for that object (see the
"Defense in depth" comment at the `report.domain_profile = analysis.domain_profile`
line). Anything nested inside `domain_profile` would be silently wiped by
that overwrite. `domain_profile_summary` must be a top-level sibling field,
the same relationship `secondary_signature_summary` has to
`secondary_signature_analysis`.

## Consistency risk to design around
Because the numeric `domain_profile` shown on the radar chart is
code-computed from `analysis.signatures` (max score per domain, scaled),
not copied from whatever Layer 2 "believes" while writing prose, there's a
real risk of the summary describing a concentration that doesn't match the
chart. Avoid this by instructing the prompt to ground the summary in which
domains `primary_constellation` and `secondary_signature_analysis` entries
actually belong to (i.e. reason from the signature list the LLM already
has, the same source `computeDomainProfile` uses) — not from the raw
`domain_profile` score field, which the LLM shouldn't try to describe
precisely in prose.

### 2. `lib/prompts/identity-report.ts`
- Add a `### domain_profile_summary` field-requirements section (near the
  existing `### domain_profile` section):
  - ~80–110 words, hard ceiling 120 — do not pad to hit the target; a
    shorter, honest summary beats one that repeats itself.
  - Ground it in which domains `primary_constellation` and
    `secondary_signature_analysis` entries belong to — not in describing
    the raw numeric `domain_profile` scores precisely (those are
    recalculated downstream and may not match what you're told here).
  - No signature names — same reasoning as `constellation_synthesis`: this
    section renders before Primary Signatures on the page, so the reader
    hasn't been introduced to any named signature yet.
  - Do not redefine what Visioning/Thinking/Connecting/Driving/Sensing
    mean — that's fixed page copy shown alongside this text, not something
    to regenerate.
  - Do not repeat `cover.identity_thesis` or `constellation_synthesis`
    content.
- Add `"domain_profile_summary": ""` to the `OUTPUT FORMAT` JSON template,
  as a sibling of `domain_profile`.
- Add `1 domain_profile_summary of ~80-110 words` to `STRUCTURAL
  CONSTRAINTS`.
- Add `domain_profile_summary is present and non-empty` to the
  pre-return verification checklist.

### 3. `lib/generate-identity-report.ts`
No computation change needed — `domain_profile_summary` is pure LLM prose,
not a code backstop candidate like the numeric `domain_profile`. Just
confirm nothing in the post-processing pipeline strips or overwrites it
(the existing `report.domain_profile = analysis.domain_profile` line only
touches the numeric field, not this one — verify that stays true after the
edit, don't just assume it from reading the diff).

### 4. `app/identity/page.tsx`
- Add `domain_profile_summary?: string;` to the page's local type for the
  report content.
- Not the `secondary_signature_summary` pattern (bare `<p>` outside the
  card, before the chart) — this is closer to how `identity_reframe`'s
  `recap` renders: plain, unstyled prose, but positioned *inside* the same
  card as the chart, directly after it:
  ```tsx
  <div className="report-section">
    <p className="eyebrow">DOMAIN PROFILE</p>
    <div className="card">
      <DomainRadarChart domainProfile={domain_profile} />
      {domain_profile_summary && <p>{domain_profile_summary}</p>}
    </div>
    <p className="documentation">{DOMAIN_PROFILE_EXPLANATION}</p>
  </div>
  ```
- The fixed `.documentation` explanation stays exactly where it is today,
  outside and after the card.
- The `domain_profile_summary &&` guard is the backward-compat handling:
  every report generated before this ships has this field `undefined`, and
  the section must render cleanly without it — no empty `<p>` inside the
  card, no error, no layout gap.
